> **这份文档是什么**：带你**从零做一个"订单事件服务"**，它从一个最简单的收消息程序开始，**每一步都被真实的业务痛点逼着往前演进**，而每一次演进恰好用上直接 Kafka（`spring-boot-starter-kafka`）的一个能力。读完，你不是"背了一堆 API"，而是**亲历了一个企业级项目怎么一步步长成**——每个 API 你都知道"它为什么存在、什么时候用"。

## 主角登场：我们要做什么

我们要做一个**订单事件服务** `order-service`。它一开始很小，但在整个文档里会**被业务推着一步步长大**——就像真实公司里的项目。

每个阶段的套路都一样：
1. **新需求/新痛点出现**（业务侧）
2. **当前做法撑不住了**（为什么需要演进）
3. **引入直接 Kafka 的某个能力解决它**（代码顺势出现）
4. **验证它有效**（curl / 控制台）

> 准备工作：起一个 Kafka（后续所有阶段共用）。
> ```bash
> docker run -d --name kafka -p 9092:9092 \
>   -e KAFKA_NODE_ID=1 -e KAFKA_PROCESS_ROLES=broker,controller \
>   -e KAFKA_LISTENERS=PLAINTEXT://:9092 -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
>   -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9092 -e KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT \
>   confluentinc/cp-kafka:latest
> ```

## 阶段 0：起步——能收到订单就行（KafkaListener）

### 痛点
公司的订单系统已经会把订单发到 Kafka 的 `orders` topic 了。你的任务很简单：**写个服务，收到订单就记一笔日志**。这是全部需求。

### 当前做法
需求这么简单，用 `spring-boot-starter-kafka` 写一个 `@KafkaListener` 就行。建项目（依赖只要 `spring-boot-starter-kafka` + `web`）：

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.0</version>
    <relativePath/>
</parent>

<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <!-- ▼ 直接用 Spring Kafka，BOM 托管版本，不用写 version -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-kafka</artifactId>
    </dependency>
</dependencies>
```

主类（收到订单，打日志——这就是全部业务逻辑）：

```java
package com.example.orderservice;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.kafka.annotation.KafkaListener;

@SpringBootApplication
public class OrderServiceApplication {

    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }

    // ▼ 收到订单，打日志。这就是全部业务逻辑。
    @KafkaListener(topics = "orders", groupId = "order-service")
    public void logOrder(String order) {
        System.out.println("[订单服务] 收到订单：" + order);
    }
}
```

配置：

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092   # ▼ 指向 Kafka
    consumer:
      group-id: order-service           # ▼ 消费组（不配的话注解里的 groupId 优先）
```

### 验证
```bash
# 往 orders 发一条
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic orders
> {"id":"ord-001","product":"手机","amount":4999}
# 应用控制台立刻打印：[订单服务] 收到订单：{...}
```

### 你学到了什么
- **`@KafkaListener(topics=..., groupId=...)`** + **`spring.kafka.bootstrap-servers`**——直接 Kafka 里没有 `destination`/`binding`，**topic 名就是代码里写的字符串**。
- 这是最朴素的"收消息"，但它能跑。**先让它跑起来，再谈优化**——这是真实项目的第一步。

> ⚠️ **诚实标注**：这版有个隐患——我们只会"收"，还不会"发"。下个阶段业务就来要这个能力了。

## 阶段 1：业务要"发"订单（KafkaTemplate）

### 痛点
产品来了新需求："用户在前端点'下单'，你的服务要**主动**产生一条订单事件发出去，让下游（库存、支付）收到。"

之前的 `@KafkaListener` 是"被动收"，现在要"主动发"。`@KafkaListener` 是事件驱动的，得有人触发它。我们需要一种"**在我代码里想发就发**"的能力。

### 引入 KafkaTemplate
Spring Kafka 提供 `KafkaTemplate`——一个让你在代码任意位置主动发消息的工具 bean。它正是为"由 HTTP 请求 / 业务事件触发发送"设计的。

加一个 Controller，用 `KafkaTemplate` 发：

```java
package com.example.orderservice;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {

    private final KafkaTemplate<String, String> kafkaTemplate;

    OrderController(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    @PostMapping("/orders")
    public String placeOrder(@RequestBody String body) {
        // ▼ 业务逻辑... 然后用 KafkaTemplate 主动发
        kafkaTemplate.send("orders", null, body);   // send(topic, key, value)
        return "已下单";
    }
}
```

> `spring-boot-starter-kafka` 自动配置了一个 `KafkaTemplate<String, String>` 注入给你——**没有 StreamBridge**，发消息就是这个 `send()`，简单直接。

### 验证
```bash
curl -X POST http://localhost:8080/orders -H "Content-Type: application/json" -d '{"id":"ord-002"}'
# → orders topic 多了一条 ord-002
# → 同时阶段0的 @KafkaListener 也收到了（它订阅 orders）
```

### 你学到了什么
- **`KafkaTemplate.send(topic, key, value)`**——主动发的标准方式，生产环境最常用。
- 一个服务里**既能收（@KafkaListener）又能发（KafkaTemplate）**，互不冲突。

> **KafkaTemplate 常用签名**（按需用）：
> `send(topic, value)` / `send(topic, key, value)` / `send(topic, partition, key, value)` / `send(Message<?>)`。返回 `CompletableFuture`，需要阻塞等待可用 `.get()`。

## 阶段 2：服务火了，扩成多实例（消费组）

### 痛点
订单服务上线后流量猛涨，单实例扛不住，你扩成了 **2 个实例**（8080、8081）。但马上发现怪事：

> 用 `kafka-console-producer` 发 1 条订单，**两个实例都收到了、都处理了一遍**！下游库存被扣了两次！

为什么？因为你的两个实例用的是**不同的消费组**（或者没固定组名，各自匿名组）——Kafka 规则：**不同消费组各自收到全量消息**。

### 用消费组解决
你想要的是：2 个实例**分担**消息（负载均衡），一条订单只被其中一个处理。规则是——**同消费组内的实例分担**。所以两个实例要用**同一个 groupId**。

改造监听器，固定组名 + 打印实例端口方便观察：

```java
package com.example.orderservice;

import org.springframework.core.env.Environment;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.kafka.annotation.KafkaListener;

@SpringBootApplication
public class OrderServiceApplication {

    private final Environment environment;

    OrderServiceApplication(Environment environment) {
        this.environment = environment;
    }

    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }

    // ▼ 关键：固定、相同的 groupId，同一个组内的实例才会分担消息
    @KafkaListener(topics = "orders", groupId = "order-service-group")
    public void logOrder(String order) {
        System.out.println("[实例" + environment.getProperty("local.server.port", "?") + "] 收到订单：" + order);
    }
}
```

两个实例**都这样配**（同一份配置，只是启动端口不同）：

```bash
mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8080
mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
```

### 验证
```bash
# 发 4 条订单
# 实例1（8080）收到 2 条，实例2（8081）收到 2 条 → 负载均衡，不重复
```

### 你学到了什么
- **消费组的核心规则**：同组=分担（负载均衡），不同组=各自全量（发布订阅）。
- **铁律**：生产环境每个消费服务**必须配固定 groupId**。不配 → 匿名自动删除组 → 重启换组 → 重复消费历史（大坑）。

> **延伸**：如果明天有个"数据分析服务"也要收订单（全量），它用**另一个 groupId**（如 `analytics-group`）——和订单服务互不干扰，各自全量。这就是发布订阅。

## 阶段 3：上线后偶发处理失败（重试）

### 痛点
上线一周，监控报警：少量订单"处理失败"。查日志，是**下游 DB 偶尔连不上**（网络抖动）——消费者处理时抛了异常，消息就没了。

你需要："**处理失败时，自动再试几次**，而不是一次失败就放弃。"

### 引入重试
直接 Kafka 的官方答案是 spring-kafka 的**非阻塞重试**——`@RetryableTopic` 注解：失败时把消息投到**重试 topic**（`orders-retry-0`、`orders-retry-1`……），按指数退避再次触发同一个监听器。配置驱动、不用写重试循环：

```java
package com.example.orderservice;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.annotation.RetryableTopic;
import org.springframework.retry.annotation.Backoff;
import org.springframework.stereotype.Component;

@Component
public class OrderConsumer {

    // ▼ 失败自动重试：attempts=3 表示 1 次原始 + 2 次重试，指数退避
    @RetryableTopic(
        topics = "orders",
        attempts = "3",
        backoff = @Backoff(delay = 1000, multiplier = 2.0, maxDelay = 10000))
    @KafkaListener(topics = "orders", groupId = "order-service-group")
    public void logOrder(String order) {
        System.out.println("[订单服务] 处理：" + order);
        if (order.contains("error")) {
            throw new RuntimeException("模拟DB连不上");   // 故意失败
        }
        System.out.println("[订单服务] 成功：" + order);
    }
}
```

### 验证
```bash
# 发一条会失败的
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic orders
> {"id":"ord-x","error":true}
# 控制台看到 "处理：..." 出现 3 次（间隔 1s、2s），3 次都失败 → 进入下个阶段的死信
```

### 你学到了什么
- **`@RetryableTopic`** + **`@Backoff`**——非阻塞重试，重试之间不卡住消费者线程。
- ⚠️ **它自动建了一堆中间 topic**（`orders-retry-0`、`orders-retry-1`）——这是特性不是 bug，重试就是靠"把消息投给下一个 topic"实现的。

## 阶段 4：救不回的死消息（死信DLT）

### 痛点
重试 3 次还失败的消息（比如真的是脏数据、或代码 bug），现在被直接丢弃了。运营来找你："这单扣款失败了，消息呢？我想人工查一下。"——没了。

**关键订单绝不能丢**。你需要："重试用尽的消息，存到一个**专门的地方**，留待人工或程序处理。"

### 引入死信（DLT）
好消息：`@RetryableTopic` 已经顺手建好了死信 topic——默认名是 `<原topic>-dlt`（这里是 `orders-dlt`）。我们只需要加一个 `@DltHandler` 兜底接收它：

```java
package com.example.orderservice;

import org.springframework.kafka.annotation.DltHandler;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.annotation.RetryableTopic;
import org.springframework.kafka.support.KafkaHeaders;
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.retry.annotation.Backoff;
import org.springframework.stereotype.Component;

@Component
public class OrderConsumer {

    // ▼ 同阶段3：失败自动重试，重试耗尽后自动进死信 topic
    @RetryableTopic(
        topics = "orders",
        attempts = "3",
        backoff = @Backoff(delay = 1000, multiplier = 2.0, maxDelay = 10000))
    @KafkaListener(topics = "orders", groupId = "order-service-group")
    public void logOrder(String order) {
        System.out.println("[订单服务] 处理：" + order);
        if (order.contains("error")) {
            throw new RuntimeException("模拟DB连不上");
        }
        System.out.println("[订单服务] 成功：" + order);
    }

    // ▼ 重试耗尽后，消息进死信 topic（orders-dlt），这里兜底记录
    @DltHandler
    public void onDlt(String order,
                      @Header(KafkaHeaders.RECEIVED_TOPIC) String dltTopic) {
        System.err.println("[死信] 重试耗尽，消息进 DLT：" + dltTopic + " / " + order);
    }
}
```

### 验证
```bash
# 发 error 消息 → 重试3次失败 → 进 orders-dlt
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 --topic orders-dlt --from-beginning
# 看到那条失败的消息；同时控制台打印 [死信] 重试耗尽...
```

### 你学到了什么
- **死信（DLT）**：重试用尽的兜底，消息不丢、可追溯。`@DltHandler` 和 `@RetryableTopic` 成对出现。
- **生产铁律**：死信 topic **必须有人盯**（告警 + 处理），否则进了死信无人知 = 变相丢失。

## 阶段 5：自定义错误兜底（DLT消费）

### 痛点
死信 topic 里攒了一批失败消息，但你想**更精细地处理错误**——比如"扣款失败的要发告警、脏数据的要记库标记"。光靠 DLT 收下来打日志不够灵活。

### 引入 DLT 头信息
spring-kafka 在投死信时，会把**原始消息的来龙去脉**一并写在 DLT 记录的 header 里（`kafka_dlt-original-topic`、`kafka_dlt-exception-fqcn`、`kafka_dlt-exception-message` 等）。在 `@DltHandler` 里读这些头，就能**按失败类型分支处理**：

```java
package com.example.orderservice;

import org.springframework.kafka.annotation.DltHandler;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.annotation.RetryableTopic;
import org.springframework.kafka.support.KafkaHeaders;
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.retry.annotation.Backoff;
import org.springframework.stereotype.Component;

@Component
public class OrderConsumer {

    @RetryableTopic(
        topics = "orders",
        attempts = "3",
        backoff = @Backoff(delay = 1000, multiplier = 2.0, maxDelay = 10000))
    @KafkaListener(topics = "orders", groupId = "order-service-group")
    public void logOrder(String order) {
        System.out.println("[订单服务] 处理：" + order);
        if (order.contains("error")) {
            throw new RuntimeException("模拟DB连不上");
        }
        System.out.println("[订单服务] 成功：" + order);
    }

    // ▼ 按失败类型精细化兜底：告警 / 记库 / 补偿
    @DltHandler
    public void onDlt(String order,
                      @Header(KafkaHeaders.DLT_ORIGINAL_TOPIC) String originalTopic,
                      @Header(KafkaHeaders.DLT_ORIGINAL_PARTITION) int originalPartition,
                      @Header(KafkaHeaders.DLT_ORIGINAL_OFFSET) long originalOffset,
                      @Header(KafkaHeaders.DLT_EXCEPTION_FQCN) String exceptionClass,
                      @Header(KafkaHeaders.DLT_EXCEPTION_MESSAGE) String exceptionMessage) {

        System.err.println("[DLT处理] 原消息：" + originalTopic + "-" + originalPartition + "@" + originalOffset);
        System.err.println("[DLT处理] 失败原因：" + exceptionClass + "：" + exceptionMessage);

        if (exceptionClass.contains("DataIntegrityViolation")) {
            System.err.println("[DLT处理] 脏数据 → 记库标记，人工处理");
        } else {
            System.err.println("[DLT处理] 其它错误 → 发告警 + 补偿");
        }
    }
}
```

> **为什么这里能拿到原始信息**：投死信时 spring-kafka 把原始 topic/partition/offset 和异常类名/消息都写进了 DLT 记录的 header——**DLT 不只是"垃圾箱"，还是带着病案袋的垃圾箱**。

### 你学到了什么
- **`@DltHandler` + DLT 头信息**（`DLT_ORIGINAL_*` / `DLT_EXCEPTION_*`）——自定义错误兜底的标准姿势，比 Stream 的错误通道更贴近 Kafka 本体、更简单。

## 阶段 6：业务流水线变复杂（流水线和定时心跳）

### 痛点
业务发展，订单处理不再是"收了就完事"，而要**串几步**：收到原始订单 → 转大写归一化 → 包一层元数据 → 才入库。每一步是独立的小函数，你想**把它们串成流水线**，而不是写成一个又长又臭的大方法。

而且，你还需要一个**定时任务**：每分钟产生一条"心跳"事件发出去，给监控系统。

### 引入方法内流水线 + @Scheduled
Stream 的函数组合（`normalize|enrich`）在直接 Kafka 里就是**普通的 Java 方法调用**——别为它造一个 topic，直接串：

```java
package com.example.orderservice;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.scheduling.annotation.EnableScheduling;

@EnableScheduling
@SpringBootApplication
public class OrderServiceApplication {

    public static void main(String[] args) {
        SpringApplication.run(OrderServiceApplication.class, args);
    }

    // ▼ 收到原始订单 → 归一化 → 加元数据 → 入库（串成流水线）
    @KafkaListener(topics = "raw-orders", groupId = "order-service-group")
    public void pipeline(String rawOrder) {
        String normalized = normalize(rawOrder);       // 1. 归一化
        String enriched = enrich(normalized);          // 2. 加元数据
        save(enriched);                                // 3. 入库
        System.out.println("[订单服务] 流水线完成：" + enriched);
    }

    private String normalize(String s) { return s.toUpperCase(); }

    private String enrich(String s) {
        return "{\"data\":\"" + s + "\",\"ts\":" + System.currentTimeMillis() + "}";
    }

    private void save(String enriched) {
        System.out.println("[订单服务] 入库：" + enriched);
    }
}
```

**定时产生心跳**（Stream 的 Supplier + poller 在直接 Kafka 里就是 `@Scheduled`）：

```java
package com.example.orderservice;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

@Component
public class HeartbeatScheduler {

    private final KafkaTemplate<String, String> kafkaTemplate;

    HeartbeatScheduler(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    // ▼ 每分钟发一条"心跳"，给监控系统（演示可改小到 5000）
    @Scheduled(fixedDelay = 60_000)
    public void heartbeat() {
        kafkaTemplate.send("heartbeats", "heartbeat-" + System.currentTimeMillis());
    }
}
```

### 验证
```bash
# 往 raw-orders 发 "phone"
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic raw-orders
> phone
# → 控制台：入库：{"data":"PHONE","ts":...}
# heartbeats topic 每 60 秒多一条 heartbeat-xxx
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 --topic heartbeats --from-beginning
```

### 你学到了什么
- **流水线 = 普通方法组合**：Stream 的函数式组合只是语法糖，直接 Kafka 里 `normalize → enrich → save` 就是方法调用。
- **定时发消息 = `@Scheduled`**：Stream 的 `Supplier` + poller 被 `@EnableScheduling` + `@Scheduled(fixedDelay)` 取代。

## 阶段 7：多输入输出（合并与分流）

### 痛点
现在订单服务要同时处理"订单流"和"用户行为流"，把它们**合并**统计；同时要把处理结果按类型**分流**到两个 topic（正常的、可疑的）。

### 引入多 topic 监听 + 条件发送
Stream 的多输入输出（Tuple）在直接 Kafka 里就是——**一个监听器听多个 topic（合并）** + **按条件 send 到不同 topic（分流）**：

```java
package com.example.orderservice;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.KafkaHeaders;
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.stereotype.Component;

@Component
public class MergeScatterProcessor {

    private final KafkaTemplate<String, String> kafkaTemplate;

    MergeScatterProcessor(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    // ▼ 多输入合并：一个监听器订阅两个 topic，用 RECEIVED_TOPIC 头区分来源
    @KafkaListener(topics = {"orders", "user-actions"}, groupId = "merge-group")
    public void merge(String msg,
                      @Header(KafkaHeaders.RECEIVED_TOPIC) String sourceTopic) {
        System.out.println("[合并] 来自 " + sourceTopic + "：" + msg);
        kafkaTemplate.send("merged", msg);                 // 合并结果发到 merged
    }

    // ▼ 多输出分流：按条件发到不同 topic
    @KafkaListener(topics = "merged", groupId = "scatter-group")
    public void scatter(String msg) {
        if (msg.contains("suspicious")) {
            kafkaTemplate.send("suspicious", msg);         // 可疑的
        } else {
            kafkaTemplate.send("normal", msg);             // 正常的
        }
    }
}
```

### 验证
```bash
# 向两个来源发消息 → 都被 [合并] 接收
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic orders
> ord-1
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic user-actions
> click-1
# 再往 merged 发一条可疑的 → 观察分流
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic merged
> suspicious-order-9
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 --topic suspicious --from-beginning
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 --topic normal --from-beginning
```

### 你学到了什么
- **多输入**：`@KafkaListener(topics = {"t1","t2"})` 一个方法听多个 topic。
- **多输出**：就是按条件调用 `kafkaTemplate.send` 到不同 topic。Stream 的 Tuple/多 binding 在这里只是"普通 if + send"。

## 阶段 8：上量了，顺序与吞吐的矛盾（分区）

### 痛点
订单量继续涨，你发现两个问题：
1. **顺序乱了**：同一笔订单的"创建→支付→发货"事件被不同实例乱序处理，状态机错乱。
2. **想加并行**：但加了并行就更乱。

你需要："**同一笔订单的事件按顺序处理，不同订单可以并行**。"

### 引入分区
Kafka 的分区机制正解此题：**相同 key 进相同分区，分区内有序**。用 orderId 当分区 key。这一阶段我们新建一个 `orders-v2` topic（6 个分区）来演示：

```bash
docker exec -it kafka kafka-topics --bootstrap-server localhost:9092 --create --topic orders-v2 --partitions 6 --replication-factor 1
```

**发送端**——用 orderId 作 key：

```java
package com.example.orderservice;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {

    private final KafkaTemplate<String, String> kafkaTemplate;

    OrderController(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    @PostMapping("/orders/{orderId}")
    public String place(@PathVariable String orderId, @RequestBody String body) {
        // ▼ 以 orderId 作分区 key：同一订单的事件进同一分区（分区内有序）
        kafkaTemplate.send("orders-v2", orderId, body);
        return "ok";
    }
}
```

**消费端**——开多个线程并行（并发度 ≤ 分区数）：

```yaml
spring:
  kafka:
    listener:
      concurrency: 3            # ▼ 3 个消费线程并行，吃满 6 个分区中的 3 个
```

```java
package com.example.orderservice;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;

@Component
public class OrderConsumer {

    @KafkaListener(topics = "orders-v2", groupId = "order-service-group")
    public void logOrder(String order) {
        // ▼ 打印线程名，验证"同 key 永远落在同一线程（分区）"
        System.out.println("[" + Thread.currentThread().getName() + "] " + order);
    }
}
```

### 验证
```bash
# 同一订单按顺序发三条事件
curl -X POST http://localhost:8080/orders/ord-100 -d '{"step":"created"}'
curl -X POST http://localhost:8080/orders/ord-100 -d '{"step":"paid"}'
curl -X POST http://localhost:8080/orders/ord-100 -d '{"step":"shipped"}'
# 控制台：三条都出现在同一个消费线程上，且顺序不乱（created→paid→shipped）
# 换一个订单 ord-101 → 落在另一个线程上（并行）
```

### 你学到了什么
- **分区**：`send(topic, key, value)` 的 **key 就是 Kafka 的分区 key**——同 key 同分区有序，不同 key 分散并行。
- **并行度上限 = 分区数**（同组内一个分区只给一个消费者）。设再多 `concurrency`、扩再多实例，超过分区数的都闲置。
- ⚠️ **顺序与吞吐的平衡**：同 key 串行（牺牲吞吐换顺序），不同 key 并行（用吞吐）。

## 阶段 9：钱相关，发送要原子且不重复（事务和幂等）

### 痛点
订单服务开始接支付了。两件事很要命：
1. **原子性**：扣款成功才发"支付成功"事件；如果先发事件、后扣款失败，下游就收到了错误事件。要"**要么全成、要么全不成**"。
2. **重复**：生产端网络抖动重试，可能把同一条消息发两次。

### 引入 Kafka 事务 + 幂等
Kafka 生产端事务：开启 `transaction-id-prefix` 后，`KafkaTemplate.send` 可以放进一个**事务**里，提交时才真正写入；失败就回滚（什么都没发）。而 **Kafka 事务会强制开启幂等**（`enable.idempotence=true`），网络重试也不会重复。

```yaml
spring:
  kafka:
    producer:
      transaction-id-prefix: tx-        # ▼ 开启事务（隐含 enable.idempotence=true）
```

> **多实例部署注意**：`transaction-id-prefix` 每个实例必须唯一，否则 transactional.id 冲突。生产一般写成 `tx-${random.uuid}`。

业务代码：

```java
package com.example.orderservice;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PaymentService {

    private final KafkaTemplate<String, String> kafkaTemplate;

    PaymentService(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    // ▼ 整个方法在同一个 Kafka 事务里：要么全成，要么全不成
    @Transactional
    public void pay(String orderId, int amount) {
        kafkaTemplate.send("payments", orderId,
                "{\"id\":\"" + orderId + "\",\"amount\":" + amount + "}");
        if (amount > 5000) {
            throw new RuntimeException("风控拒绝：单笔超过 5000");   // 模拟业务失败
        }
    }
}
```

配一个触发它的 Controller：

```java
package com.example.orderservice;

import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class PaymentController {

    private final PaymentService paymentService;

    PaymentController(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    @PostMapping("/payments/{orderId}/{amount}")
    public String pay(@PathVariable String orderId, @PathVariable int amount) {
        paymentService.pay(orderId, amount);
        return "已支付";
    }
}
```

> **事务管理器从哪来**：Boot 看到 `spring.kafka.producer.transaction-id-prefix` 且项目里没有别的 `TransactionManager` 时，会自动配置一个 `KafkaTransactionManager`，`@Transactional` 就会用它。**如果项目同时有 DB 事务管理器**，要显式指定：`@Transactional("kafkaTransactionManager")`，或用 ChainedTransactionManager 把 DB + Kafka 绑在一起（见 [04 方向A：Outbox](./04-生产级进阶-Outbox与Schema与分区调优.md)）。

### 验证
```bash
curl -X POST http://localhost:8080/payments/p1/1000   # 成功
curl -X POST http://localhost:8080/payments/p2/9999   # 500（风控拒绝）
# 检查 payments topic：只有 p1，没有 p2 —— 事务回滚了那条失败的发送
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 --topic payments --from-beginning
```

### 你学到了什么
- **Kafka 事务**：`transaction-id-prefix` + `@Transactional`，发送原子化。
- **幂等**（`enable.idempotence=true`）：事务会自动开启；不想要事务、只想防重复时，可单独配 `spring.kafka.producer.properties.enable.idempotence: true`。幂等解决"生产端重试导致重复"，**消费者端的重复消费**要靠消费方幂等（幂等表去重，见 [03 第4章](./03-事件驱动微服务端到端实战.md)）。

## 阶段 10：重启后不重复不丢失（offset管理）

### 痛点
流量继续涨，你的消费者又出事了：**服务重启后，一批订单被重复处理**（或丢了）。原因是你没管 offset——Kafka 靠 offset 记录"消费到哪了"。

### 引入手动提交 offset
默认 `enable-auto-commit: true`：每 5 秒自动提交一次。问题：**"处理成功但没提交就崩了"→ 重启重复消费**；或**"提交了但没处理完"→ 崩了丢消息**。

改成手动提交，**处理成功才 ack**：

```yaml
spring:
  kafka:
    consumer:
      enable-auto-commit: false      # ▼ 关掉自动提交
    listener:
      ack-mode: manual               # ▼ 手动 ack：处理完再 acknowledge()
```

```java
package com.example.orderservice;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.stereotype.Component;

@Component
public class OrderConsumer {

    @KafkaListener(topics = "orders", groupId = "order-service-group")
    public void handle(String order, Acknowledgment ack) {
        boolean ok = processSafely(order);     // 业务处理
        if (ok) {
            ack.acknowledge();                 // ▼ 成功才提交 offset
        } else {
            // 不 ack → 这条的 offset 不会被提交 → 重启后会被重新消费（at-least-once）
            throw new RuntimeException("处理失败，不回提交 offset");
        }
    }

    private boolean processSafely(String order) {
        System.out.println("[订单服务] 处理：" + order);
        return !order.contains("bad");         // 模拟"这条处理不了"
    }
}
```

> 失败的那条如果叠加了阶段 3 的 `@RetryableTopic`，会先重试、再进死信——**重试 + 死信是"处理失败"的兜底，手动 ack 是"控制提交时机"的手段**，两者配合。上面代码为聚焦 offset 语义，简化为纯 `@KafkaListener`。

### 验证
```bash
# 查看这个消费组的消费进度 / 积压
docker exec -it kafka kafka-consumer-groups --bootstrap-server localhost:9092 --group order-service-group --describe
# CURRENT-OFFSET 当前消费到哪；LOG-END-OFFSET 队列尾；LAG 积压
# 发一条 ok 消息 → CURRENT-OFFSET 前进；发一条 bad 消息 → 进死信，LAG 归零不阻塞
```

### 你学到了什么
- **offset 管理**：`enable-auto-commit: false` + `ack-mode: manual` + `Acknowledgment`——你自己决定提交点。
- **at-least-once 是底线**：Kafka 至少投递一次，消费者**必须幂等**（见阶段 9），再配合手动 ack 精确控制。
- **查进度**：`kafka-consumer-groups --describe` 是消费组的"仪表盘"。

## 阶段 11：单条处理太慢（批处理）

### 痛点
运营提了新需求："别一条条处理，**攒一批一起处理**，省 DB 往返。"单条处理每条都要查/写一次 DB，太慢。

### 引入批量监听
Spring Kafka 支持**批量消费**：一次 poll 拿一批消息，监听器方法收到一个 `List`：

```yaml
spring:
  kafka:
    listener:
      type: batch                  # ▼ 开启批量模式
    consumer:
      properties:
        max.poll.records: 50       # ▼ 每次 poll 最多 50 条
```

```java
package com.example.orderservice;

import java.util.List;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;

@Component
public class OrderBatchConsumer {

    @KafkaListener(topics = "orders", groupId = "order-service-group")
    public void batchProcess(List<String> orders) {
        System.out.println("[批处理] 一次处理 " + orders.size() + " 条：" + orders);
        // 批量入库：一次 insert 一批，省往返
    }
}
```

> ⚠️ **注意**：`type: batch` 是**全局的**（影响默认容器工厂下所有监听器）。这一阶段把 orders 的监听器改成批量演示；生产里"单/批混用"需要自定义 ContainerFactory（超出本篇范围）。

### 验证
```bash
# 快速连发 10 条
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic orders
> 1
> 2
...（10条）
# 控制台：一次处理 N 条：...（合并成少数几次打印）
```

### 你学到了什么
- **批处理**：`listener.type: batch` + `List<String>` 入参 + `max.poll.records` 控制批量大小。
- 批量入库能把吞吐提高一个数量级；代价是单条失败的处理粒度变粗（整批回退/重试）。

## 阶段 12：事件结构要改（Schema Registry）

### 痛点
运营要给订单加个 `couponCode` 字段。你改了事件结构重新部署，结果**库存服务（旧版本）反序列化崩溃**，消息堆积——因为旧消费者不认识新结构。

你需要："**事件结构能演进，且不崩老消费者**。"

### 引入 Schema Registry
用 Avro + Confluent Schema Registry：消息只带 schema ID，Registry 管版本和兼容性。直接 Kafka 里就是给 producer/consumer 配 Confluent 的序列化器（不经过任何 Stream 抽象）：

```xml
<dependency>
    <groupId>io.confluent</groupId>
    <artifactId>kafka-avro-serializer</artifactId>
    <version>7.6.0</version>
</dependency>
```

```yaml
spring:
  kafka:
    producer:
      properties:
        key.serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
        value.serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
        schema.registry.url: http://localhost:8081
    consumer:
      properties:
        key.deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer
        value.deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer
        schema.registry.url: http://localhost:8081
        specific.avro.reader: true
      group-id: order-service-group
```

> 需要先起一个 Schema Registry（它能连到你的 Kafka 即可）：
> ```bash
> docker run -d --name schema-registry -p 8081:8081 \
>   -e SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS=host.docker.internal:9092 \
>   -e SCHEMA_REGISTRY_HOST_NAME=schema-registry \
>   confluentinc/cp-schema-registry:7.6.0
> ```
> 如果网络不通，把 `SCHEMA_REGISTRY_KAFKASTORE_BOOTSTRAP_SERVERS` 换成你的 Kafka 地址。

> 加字段时，Registry 按 **BACKWARD 兼容**（默认）校验——只加字段（有默认值）OK，删字段会被拒绝。**把"隐式契约"变成"显式契约"**，改结构不再心惊胆战。详见 [04 方向B](./04-生产级进阶-Outbox与Schema与分区调优.md)。

## 阶段 13：运维要看得见（可观测性）

### 痛点
系统终于稳定跑起来了，但线上出问题时**两眼一抹黑**：消费速率多少？积压多少？发送失败率？没有指标，只能靠用户投诉发现故障。

### 引入 Actuator + Micrometer
`spring-boot-starter-kafka` + Actuator 会自动暴露 Kafka 的生产者/消费者指标（Micrometer，`kafka_*` 前缀）。加依赖：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

打开端点：

```yaml
spring:
  kafka:
    listener:
      observation-enabled: true      # ▼ 监听器埋点（处理耗时等）
management:
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus
```

### 验证
```bash
# 健康检查：kafka 是否连得上
curl -s http://localhost:8080/actuator/health | jq .kafka
# → {"status":"UP"}

# 看 Kafka 指标（Actuator 是点分格式，Prometheus 是下划线格式）
curl -s "http://localhost:8080/actuator/metrics" | grep kafka
curl -s http://localhost:8080/actuator/prometheus | grep kafka
```

必盯的指标：
- `kafka_consumer_fetch_manager_records_consumed_total`：消费速率。
- `kafka_consumer_fetch_manager_records_lag`：**消费积压（lag）——生产必盯的指标**。
- `kafka_producer_record_send_total` / `kafka_producer_record_error_total`：发送量/错误量。

> **生产铁律**：lag 是 Kafka 消费者的"体检报告"。**lag 持续上涨 = 消费追不上生产**，先看阶段 8 的并发是不是没吃满分区。

### 你学到了什么
- **可观测性**：`spring-boot-starter-actuator` + Micrometer 自动暴露 `kafka_*` 指标，健康检查能显示 Kafka 连接状态。
- Stream 的可观测性也是这一套（底层都是 Micrometer）——**换成直接 Kafka，监控指标一个不少**。

## 演进回顾：一张图看懂每一步为什么走

```
阶段0  起步：能收订单就行                    → @KafkaListener
  │    （只会收，不会发）
  ▼
阶段1  业务要"发"订单                        → KafkaTemplate（主动发）
  │    （单实例扛不住）
  ▼
阶段2  扩多实例，不想重复处理                → 消费组（同 groupId 分担）
  │    （偶发 DB 抖动，消息丢）
  ▼
阶段3  失败要自动重试                        → @RetryableTopic + @Backoff
  │    （重试也救不回的）
  ▼
阶段4  死消息不能丢                          → @DltHandler（DLT 死信）
  │    （要精细处理错误）
  ▼
阶段5  自定义错误兜底                        → DLT 头信息 + 按异常类型分支
  │    （处理变复杂，要串步骤+定时任务）
  ▼
阶段6  业务流水线                            → 方法内流水线 + @Scheduled 心跳
  │    （要合并/分流多流）
  ▼
阶段7  多输入输出                            → 多 topic 监听 + 条件 send
  │    （上量，顺序/吞吐矛盾）
  ▼
阶段8  分区                                  → key 分区 + concurrency（同 key 有序）
  │    （钱相关，发送要原子且不重复）
  ▼
阶段9  事务 + 幂等                           → transaction-id-prefix + @Transactional
  │    （重启后重复处理 / 想控制提交时机）
  ▼
阶段10 offset 管理                           → enable-auto-commit=false + 手动 ack
  │    （单条处理太慢）
  ▼
阶段11 批处理                                → listener.type=batch（List<>）
  │    （事件结构要改，怕崩消费者）
  ▼
阶段12 Schema Registry                      → Avro + 版本兼容
  │    （运维要看得见）
  ▼
阶段13 可观测性                              → Actuator + Micrometer（kafka_* 指标）
```

**每一步都不是"为了学 API"，而是"业务逼到这了，正好用上这个能力"**。这就是企业级项目真实的生长方式，也是你该记住的——**先有痛点，再有技术**。
