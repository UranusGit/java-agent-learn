## 主角登场：我们要做什么

我们要做一个**订单事件服务** `order-service`。它一开始很小，但在整个文档里会**被业务推着一步步长大**——就像真实公司里的项目。

每个阶段的套路都一样：
1. **新需求/新痛点出现**（业务侧）
2. **当前做法撑不住了**（为什么需要演进）
3. **引入 Stream 的某个能力解决它**（代码顺势出现）
4. **验证它有效**（curl / 控制台）

> 准备工作：起一个 Kafka（后续所有阶段共用）。
> ```bash
> docker run -d --name kafka -p 9092:9092 \
>   -e KAFKA_NODE_ID=1 -e KAFKA_PROCESS_ROLES=broker,controller \
>   -e KAFKA_LISTENERS=PLAINTEXT://:9092 -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
>   -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9092 -e KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT \
>   confluentinc/cp-kafka:latest
> ```

## 阶段 0：起步——能收到订单就行（Consumer）

### 痛点
公司的订单系统已经会把订单发到 Kafka 的 `orders` topic 了。你的任务很简单：**写个服务，收到订单就记一笔日志**。这是全部需求。

### 当前做法
需求这么简单，用 Spring Cloud Stream 写一个 `Consumer` 就行。建项目（依赖只要 `spring-cloud-starter-stream-kafka` + `web`），写主类：

```java
@SpringBootApplication
public class OrderServiceApplication {
    public static void main(String[] args) { SpringApplication.run(OrderServiceApplication.class, args); }

    // ▼ 收到订单，打日志。这就是全部业务逻辑。
    @Bean
    public Consumer<String> logOrder() {
        return order -> System.out.println("[订单服务] 收到订单：" + order);
    }
}
```

配置：
```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
  cloud:
    function:
      definition: logOrder          # ▼ 告诉框架：用 logOrder 这个函数
    stream:
      bindings:
        logOrder-in-0:              # ▼ binding 名 = 函数名 + "-in-0"
          destination: orders       # ▼ 订阅 orders topic
          group: order-service      # ▼ 消费组
```

### 验证
```bash
# 往 orders 发一条
docker exec -it kafka kafka-console-producer --bootstrap-server localhost:9092 --topic orders
> {"id":"ord-001","product":"手机","amount":4999}
# 应用控制台立刻打印：[订单服务] 收到订单：{...}
```

### 你学到了什么
- **Consumer** + **`spring.cloud.function.definition`** + **binding 命名 `<func>-in-0`** + **destination/group**。
- 这是最朴素的"收消息"，但它能跑。**先让它跑起来，再谈优化**——这是真实项目的第一步。

> ⚠️ **诚实标注**：这版有个隐患——我们只会"收"，还不会"发"。下个阶段业务就来要这个能力了。

## 阶段 1：业务要"发"订单（StreamBridge）

### 痛点
产品来了新需求："用户在前端点'下单'，你的服务要**主动**产生一条订单事件发出去，让下游（库存、支付）收到。"

之前的 `Consumer` 是"被动收"，现在要"主动发"。`Consumer` 做不了这事——它是事件驱动的，得有人触发它。我们需要一种"**在我代码里想发就发**"的能力。

### 引入 StreamBridge
Spring Cloud Stream 提供 `StreamBridge`——一个让你在代码任意位置主动发消息的工具 bean。它正是为"由 HTTP 请求 / 业务事件触发发送"设计的。

加一个 Controller，用 `StreamBridge` 发：

```java
@RestController
class OrderController {
    private final StreamBridge bridge;
    OrderController(StreamBridge bridge) { this.bridge = bridge; }

    @PostMapping("/orders")
    public String placeOrder(@RequestBody String body) {
        // ▼ 业务逻辑... 然后用 StreamBridge 主动发
        bridge.send("placeOrder-out-0", body);
        return "已下单";
    }
}
```

配置（给 binding 起个语义化的 destination）：
```yaml
spring:
  cloud:
    stream:
      output-bindings: placeOrder-out-0   # ▼ 启动时预创建（不然首次 send 才懒创建）
      bindings:
        placeOrder-out-0:
          destination: orders             # ▼ 发到 orders topic
```

### 验证
```bash
curl -X POST http://localhost:8080/orders -H "Content-Type: application/json" -d '{"id":"ord-002"}'
# → orders topic 多了一条 ord-002
# → 同时阶段0的 Consumer 也收到了（它订阅 orders）
```

### 你学到了什么
- **StreamBridge.send(bindingName, data)**——主动发的标准方式，生产环境最常用。
- **`output-bindings`** 预创建 binding。
- 一个服务里**既能收（Consumer）又能发（StreamBridge）**，互不冲突。

> **StreamBridge 全部签名**（已校验，按需用）：
> `send(bindingName, data)` / `send(bindingName, data, MimeType)` / `send(bindingName, binderType, data)` / `send(bindingName, binderType, data, MimeType)`。

## 阶段 2：服务火了，扩成多实例（消费组）

### 痛点
订单服务上线后流量猛涨，单实例扛不住，你扩成了 **2 个实例**（8080、8081）。但马上发现怪事：

> 用 `kafka-console-producer` 发 1 条订单，**两个实例都收到了、都处理了一遍**！下游库存被扣了两次！

为什么？因为你的两个实例用的是**不同的消费组**（或者没固定组名，各自匿名组）——Kafka 规则：**不同消费组各自收到全量消息**。

### 用消费组解决
你想要的是：2 个实例**分担**消息（负载均衡），一条订单只被其中一个处理。规则是——**同消费组内的实例分担**。所以两个实例要用**同一个 group 名**。

配置（两个实例都这样配）：
```yaml
spring:
  cloud:
    stream:
      bindings:
        logOrder-in-0:
          destination: orders
          group: order-service-group   # ▼ 关键：固定、相同的消费组名
```

### 验证
```bash
# 发 4 条订单
# 实例1（8080）收到 2 条，实例2（8081）收到 2 条 → 负载均衡，不重复
```

### 你学到了什么
- **消费组的核心规则**：同组=分担（负载均衡），不同组=各自全量（发布订阅）。
- **铁律**：生产环境每个消费服务**必须配固定 group 名**。不配 → 匿名自动删除组 → 重启换组 → 重复消费历史（大坑）。

> **延伸**：如果明天有个"数据分析服务"也要收订单（全量），它用**另一个 group**（如 `analytics-group`）——和订单服务互不干扰，各自全量。这就是发布订阅。

## 阶段 3：上线后偶发处理失败（重试）

### 痛点
上线一周，监控报警：少量订单"处理失败"。查日志，是**下游 DB 偶尔连不上**（网络抖动）——消费者处理时抛了异常，消息就没了。

你需要："**处理失败时，自动再试几次**，而不是一次失败就放弃。"

### 引入重试
Spring Cloud Stream 内建重试——配置即可，不用写代码。

```yaml
spring:
  cloud:
    stream:
      bindings:
        logOrder-in-0:
          destination: orders
          group: order-service-group
          consumer:
            max-attempts: 3                  # ▼ 最多试 3 次（含首次）
            back-off-initial-interval: 1000  # ▼ 首次重试等 1s
            back-off-multiplier: 2.0         # ▼ 每次翻倍：1s → 2s
            back-off-max-interval: 10000     # ▼ 单次最长 10s
```

业务代码模拟一下失败，看效果：
```java
@Bean
public Consumer<String> logOrder() {
    return order -> {
        System.out.println("[订单服务] 处理：" + order);
        if (order.contains("error")) throw new RuntimeException("模拟DB连不上");  // 故意失败
        System.out.println("[订单服务] 成功：" + order);
    };
}
```

### 验证
```bash
# 发一条会失败的
docker exec -it kafka kafka-console-producer ... --topic orders
> {"id":"ord-x","error":true}
# 控制台看到 "处理：..." 出现 3 次（间隔 1s、2s），3 次都失败 → 进入下个阶段的死信
```

### 你学到了什么
- **重试配置**：`max-attempts` + `back-off-*`（指数退避）。
- ⚠️ **重要限制**：框架级重试**只对命令式 `Consumer` 生效**，对响应式 `Consumer<Flux<>>` 无效（阶段10会讲为什么）。

## 阶段 4：救不回的死消息（死信）

### 痛点
重试 3 次还失败的消息（比如真的是脏数据、或代码 bug），现在被直接丢弃了。运营来找你："这单扣款失败了，消息呢？我想人工查一下。"——没了。

**关键订单绝不能丢**。你需要："重试用尽的消息，存到一个**专门的地方**，留待人工或程序处理。"

### 引入死信（DLQ）
死信机制：重试用尽的消息不发往虚空，而是发到一个**死信 topic**。Kafka binder 配置：

```yaml
spring:
  cloud:
    stream:
      bindings:
        logOrder-in-0:
          consumer:
            max-attempts: 3
      kafka:
        bindings:
          logOrder-in-0:
            consumer:
              enable-dlq: true            # ▼ Kafka binder 开死信
              dlq-name: orders-dlq        # ▼ 死信 topic 名
```

### 验证
```bash
# 发 error 消息 → 重试3次失败 → 进 orders-dlq
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 --topic orders-dlq --from-beginning
# 看到那条失败的消息
```

### 你学到了什么
- **死信**：重试用尽的兜底，消息不丢、可追溯。
- **生产铁律**：死信 topic **必须有人盯**（告警 + 处理），否则进了死信无人知 = 变相丢失。

> **Kafka vs RabbitMQ 死信配置不同**（这就是 Binder 抽象"中间件差异"处）：Kafka 用 `enable-dlq`，RabbitMQ 用 `auto-bind-dlq` + `republish-to-dlq`。但业务代码一样。

## 阶段 5：自定义错误兜底（错误处理）

### 痛点
死信 topic 里攒了一批失败消息，但你想**更精细地处理错误**——比如"扣款失败的要发告警、脏数据的要记库标记"。光靠死信 topic 不够灵活。

### 引入错误通道
消息处理失败时，框架把异常发到一个**错误通道**（名字 `<destination>.<group>.errors`）。用 `@ServiceActivator` 订阅它，自定义处理：

```java
import org.springframework.integration.annotation.ServiceActivator;
import org.springframework.messaging.Message;
import org.springframework.stereotype.Component;

@Component
public class OrderErrorHandler {
    // ▼ 订阅错误通道：destination.group.errors
    @ServiceActivator(inputChannel = "orders.order-service-group.errors")
    public void handleError(Message<?> errorMessage) {
        System.err.println("[错误处理] 订单处理失败：" + errorMessage.getPayload());
        // 发告警、记库、补偿...
    }
}
```

> ⚠️ **新手常犯的错**：错误通道是 Spring Integration 的 `MessageChannel`，**用 `@ServiceActivator`** 订阅，**不是**配一个 `Consumer` binding（那样是把错误通道当 topic，方向错了）。

### 你学到了什么
- **错误通道** `<destination>.<group>.errors` + `@ServiceActivator`——自定义错误兜底。

## 阶段 6：业务流水线变复杂（函数组合 + Supplier/Function）

### 痛点
业务发展，订单处理不再是"收了就完事"，而要**串几步**：收到原始订单 → 转大写归一化 → 包一层元数据 → 才入库。每一步是独立的小函数，你想**把它们串成流水线**，而不是写成一个又长又臭的大方法。

而且，你还需要一个**定时任务**：每分钟产生一条"心跳"事件发出去，给监控系统。

### 引入 Function（处理）+ Supplier（产生）+ 函数组合

**Function（收一条、处理、产一条）**：
```java
@Bean
public Function<String, String> normalize() { return String::toUpperCase; }   // 归一化

@Bean
public Function<String, String> enrich() { return s -> "{\"data\":\"" + s + "\",\"ts\":" + System.currentTimeMillis() + "}"; }  // 加元数据
```

**Supplier（定时产生）**：
```java
@Bean
public Supplier<String> heartbeat() { return () -> "heartbeat-" + System.currentTimeMillis(); }
```

**函数组合**（用 `|` 把 normalize 和 enrich 串起来）：
```yaml
spring:
  cloud:
    function:
      definition: heartbeat;normalize|enrich     # ▼ 分号=多个独立函数；管道=组合
    stream:
      function:
        bindings:
          normalize|enrich-in-0: pipeline-in     # ▼ 组合名太长，重命名
      bindings:
        heartbeat-out-0:
          destination: heartbeats
        pipeline-in:
          destination: raw-orders
        normalize|enrich-out-0:
          destination: enriched-orders
      poller:
        fixed-delay: 60000                       # ▼ Supplier 每60秒触发
```

### 验证
```bash
# 往 raw-orders 发 "phone"
# → normalize 变 PHONE → enrich 变 {"data":"PHONE","ts":...} → 进 enriched-orders
# heartbeats topic 每60秒多一条 heartbeat-xxx
```

### 你学到了什么
- **Function**（入+出，处理器）、**Supplier**（无入有出，源）。
- **函数组合** `|`（串成流水线）、**`;`**（多个独立函数）、**poller**（Supplier 轮询触发）。

## 阶段 7：多输入输出——合并/分流多个流

### 痛点
现在订单服务要同时处理"订单流"和"用户行为流"，把它们**合并**统计；同时要把处理结果按类型**分流**到两个 topic（正常的、可疑的）。

### 引入多输入输出（Tuple）
一个函数可以消费多个流、产生多个流，用 Reactor 的 `Tuple`：

```java
import reactor.util.function.Tuple2;
import reactor.util.function.Tuples;
import reactor.core.publisher.Flux;
import java.util.function.Function;

// ▼ 两输入（订单 + 用户行为）→ 一输出（合并）
@Bean
public Function<Tuple2<Flux<String>, Flux<String>>, Flux<String>> merge() {
    return tuple -> Flux.merge(tuple.getT1(), tuple.getT2());
}
// binding：merge-in-0、merge-in-1、merge-out-0

// ▼ 一输入 → 两输出（分流）
@Bean
public Function<Flux<String>, Tuple2<Flux<String>, Flux<String>>> scatter() {
    return flux -> {
        // 按条件拆成两个流（简化）
        return Tuples.of(flux.filter(s -> !s.contains("suspicious")),
                         flux.filter(s -> s.contains("suspicious")));
    };
}
// binding：scatter-in-0、scatter-out-0、scatter-out-1
```

```yaml
spring:
  cloud:
    function:
      definition: merge;scatter
    stream:
      bindings:
        merge-in-0:    { destination: orders }
        merge-in-1:    { destination: user-actions }
        merge-out-0:   { destination: merged }
        scatter-in-0:  { destination: merged }
        scatter-out-0: { destination: normal }
        scatter-out-1: { destination: suspicious }
```

### 你学到了什么
- **多输入**（`-in-0`/`-in-1` + Tuple）、**多输出**（`-out-0`/`-out-1`）。

## 阶段 8：公司要用 RabbitMQ（多 Binder）

### 痛点
公司收购了一家子公司，他们的系统用的是 **RabbitMQ**，不是 Kafka。老板说："你的订单服务要能**从 Kafka 收、发到 RabbitMQ**，把两边打通。"

如果你的代码和 Kafka 死绑，这下要大改。但你用的是 Spring Cloud Stream——**换中间件不改业务代码**。

### 引入多 Binder
加 RabbitMQ starter，配两个 binder，binding 指定用哪个：

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-stream-rabbit</artifactId>
</dependency>
```

```java
@Bean
public Function<String, String> bridge() { return s -> s; }   // 收啥发啥
```

```yaml
spring:
  cloud:
    function:
      definition: bridge
    stream:
      binders:                         # ▼ 定义两个 binder（已校验）
        kafkaBinder:
          type: kafka
          environment:
            spring.cloud.stream.kafka.binder.brokers: localhost:9092
        rabbitBinder:
          type: rabbit
          environment:
            spring.rabbitmq.host: localhost
      bindings:
        bridge-in-0:
          destination: from-kafka
          binder: kafkaBinder          # ▼ 输入用 Kafka
        bridge-out-0:
          destination: to-rabbit
          binder: rabbitBinder         # ▼ 输出用 RabbitMQ
```

### 验证
往 Kafka `from-kafka` 发消息 → 出现在 RabbitMQ `to-rabbit`。**同一个 Function，桥接了两个中间件，业务代码一个字没改**。

### 你学到了什么
- **多 Binder**：`spring.cloud.stream.binders.*`（type+environment）+ binding 用 `binder:` 指定。
- 这就是 Stream 抽象的价值——**换中间件不改代码**。

## 阶段 9：上量了，顺序与吞吐的矛盾（分区）

### 痛点
订单量继续涨，你发现两个问题：
1. **顺序乱了**：同一笔订单的"创建→支付→发货"事件被不同实例乱序处理，状态机错乱。
2. **想加并行**：但加了并行就更乱。

你需要："**同一笔订单的事件按顺序处理，不同订单可以并行**。"

### 引入分区
Kafka 的分区机制正解此题：**相同 key 进相同分区，分区内有序**。用 orderId 当分区 key：

```java
@RestController
class OrderController {
    private final StreamBridge bridge;
    OrderController(StreamBridge b) { this.bridge = b; }

    @PostMapping("/orders")
    public String place(@RequestBody Order o) {
        // ▼ 用 Message 带 partitionKey header（orderId）
        bridge.send("placeOrder-out-0", MessageBuilder.withPayload(o.toJson())
                .setHeader("partitionKey", o.getId()).build());
        return "ok";
    }
}
```

```yaml
spring:
  cloud:
    stream:
      bindings:
        placeOrder-out-0:
          destination: orders
          producer:
            partition-count: 6                            # ▼ 6 个分区
            partition-key-expression: headers['partitionKey']  # ▼ 同 key 进同分区（有序）
```

### 你学到了什么
- **分区**：`partition-count` + `partition-key-expression`。
- **顺序与并行的平衡**：同 key 同分区有序，不同 key 分散并行。
- ⚠️ **并行度上限 = 分区数**（同组内一个分区只给一个消费者）。设再多 `concurrency`、扩再多实例，超过分区数的都闲置。

## 阶段 10：换响应式栈（响应式 Function + 批处理）

### 痛点
订单服务的下游开始用响应式服务（WebFlux），团队要求消费者也用响应式风格（`Flux`），好和非阻塞的下游对接。而且运营提了新需求："别一条条处理，**攒一批一起处理**，省 DB 往返。"

### 引入响应式 Function + 批处理

**响应式 Function**（用 `Flux`）：
```java
import reactor.core.publisher.Flux;
@Bean
public Function<Flux<String>, Flux<String>> reactiveProcess() {
    return flux -> flux.map(String::toUpperCase)
            // ▼ 注意：框架级重试（阶段3）对响应式无效，要自己处理
            .onErrorResume(e -> Flux.empty());
}
```

**批处理**（`Consumer<List<>>`，一次处理一批）：
```java
@Bean
public Consumer<List<String>> batchProcess() {
    return batch -> System.out.println("[批处理] 一次处理 " + batch.size() + " 条：" + batch);
}
```

```yaml
spring:
  cloud:
    stream:
      bindings:
        batchProcess-in-0:
          destination: orders
          group: order-service-group
          consumer:
            batch-mode: true          # ▼ 开启批处理
```

### 你学到了什么
- **响应式 Function** `Function<Flux<>,Flux<>>`。
- ⚠️ **两个真相**（已校验）：① 框架级重试对响应式无效（自己用 `.retryWhen`）；② 普通非响应式 binder 下用 `Flux` 没有真背压（响应式 binder 已废弃，见 [02 第4章](./02-Spring-Cloud-Stream进阶实战.md)）。
- **批处理**：`batch-mode: true` + `Consumer<List<>>`，批量入库更快。

## 阶段 11：事件结构要改（Schema Registry）

### 痛点
运营要给订单加个 `couponCode` 字段。你改了事件结构重新部署，结果**库存服务（旧版本）反序列化崩溃**，消息堆积——因为旧消费者不认识新结构。

你需要："**事件结构能演进，且不崩老消费者**。"

### 引入 Schema Registry
用 Avro + Confluent Schema Registry：消息只带 schema ID，Registry 管版本和兼容性。

```xml
<dependency>
    <groupId>io.confluent</groupId>
    <artifactId>kafka-avro-serializer</artifactId>
    <version>7.6.0</version>
</dependency>
```

```yaml
spring:
  cloud:
    stream:
      kafka:
        binder:
          producer-properties:
            key.serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
            value.serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
            schema.registry.url: http://localhost:8081
          consumer-properties:
            key.deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer
            value.deserializer: io.confluent.kafka.serializers.KafkaAvroDeserializer
            schema.registry.url: http://localhost:8081
            specific.avro.reader: true
      bindings:
        avroOut-out-0:
          destination: orders-avro
          producer:
            use-native-encoding: true
```

> 加字段时，Registry 按 BACKWARD 兼容（默认）校验——只加字段（有默认值）OK，删字段会被拒绝。**把"隐式契约"变成"显式契约"**，改结构不再心惊胆战。详见 [04 方向B](./04-生产级进阶-Outbox与Schema与分区调优.md)。

## 演进回顾：一张图看懂每一步为什么走

```
阶段0  起步：能收订单就行                    → Consumer
  │    （只会收，不会发）
  ▼
阶段1  业务要"发"订单                        → StreamBridge（主动发）
  │    （单实例扛不住）
  ▼
阶段2  扩多实例，不想重复处理                → 消费组（同组分担）
  │    （偶发 DB 抖动，消息丢）
  ▼
阶段3  失败要自动重试                        → 重试（max-attempts）
  │    （重试也救不回的）
  ▼
阶段4  死消息不能丢                          → 死信 DLQ
  │    （要精细处理错误）
  ▼
阶段5  自定义错误兜底                        → 错误通道 + @ServiceActivator
  │    （处理变复杂，要串步骤+定时任务）
  ▼
阶段6  业务流水线                            → Function/Supplier + 函数组合
  │    （要合并/分流多流）
  ▼
阶段7  多输入输出                            → Tuple 多 in/out
  │    （公司要用 RabbitMQ）
  ▼
阶段8  多中间件                              → 多 Binder（换中间件不改代码）
  │    （上量，顺序/吞吐矛盾）
  ▼
阶段9  分区                                  → partition-count + key（同key有序）
  │    （下游响应式 + 要批处理）
  ▼
阶段10 响应式 + 批处理                       → Flux Function + batch-mode
  │    （事件结构要改，怕崩消费者）
  ▼
阶段11 Schema Registry                      → Avro + 版本兼容
```

**每一步都不是"为了学 API"，而是"业务逼到这了，正好用上这个能力"**。这就是企业级项目真实的生长方式，也是你该记住的——**先有痛点，再有技术**。
