## 1. 六个关键设计复盘

### 1.1 为什么降噪是"确定性先行、LLM 收尾"

三层流水线（L1 去重 → L2 聚类 → L3 LLM 简报）的本质是**频率×成本匹配**：告警是每秒级的高频流，全量过 LLM 的成本不可承受。确定性算法（fingerprint 去重、embedding 聚类、Z-Score 异常）毫秒级零成本过滤掉 95%+ 流量，LLM 只对"可疑簇"做最终叙事。这与 [教程 38-Agent性能优化 §级联路由]、[附录 10-语义缓存与性能/00-语义缓存实现 §相似查询缓存] 是同构思想。**代价**：LLM 覆盖不到的边界靠规则简报兜底——宁可简报粗糙，不可丢告警（ADR-407）。

### 1.2 为什么 HITL 在 ToolCallingManager 而非 Advisor

处置动作是**工具执行**，不是 ChatClient 调用。Advisor 环绕整个 ChatClient 边界，拦不到"工具意图返回后、执行前"；ToolCallingManager 装饰器正好插在 LLM 决定调工具与工具真正执行之间（[附录 05-SpringAI2-API基准/02 §1.3]）。这是本体系 HITL 铁律的又一次落地（[教程 28-Human-in-the-Loop与审批流 §3]）。

### 1.3 为什么长任务用 Checkpoint（教程 40）而非自研"断点落库"

**checkpoint 不是"把状态存一下"**：它是"保存恢复所需最小状态（计划/已完成步骤/预算/幂等键），崩溃后从最近检查点续跑、不重跑已完成步骤、不重复副作用"。v5 采用 [教程 40] 的 Checkpoint 机制（可手写、零外部依赖），覆盖"进程重启续跑"的核心运维场景。跨进程/跨主机的 durable execution（如 Temporal）需要外部运行时，记为生产演进方向（ADR-415 备选）。**选型代价**：本机重启场景需自写恢复逻辑；跨主机场景需升级到 durable execution。

### 1.4 为什么知识飞轮要"证据/假设分离"

postmortem 的「观察到的客观事实」与「AI 生成的假设」分开存储检索——因为 AI 假设可能错，一旦被当成已验证根因会污染后续所有 RCA（[调研 AIOps 2026 §知识飞轮]）。检索只信 facts，hypotheses 仅作提示并标注"未验证"。这是**防知识污染**的架构纪律，与 [教程 41-数据飞轮与持续改进] 一脉相承。

### 1.5 为什么容量按 P95 而非均值

均值会低估峰值（"平均 60% CPU"但峰值 95%）；按 P95 置信上界配置容量匹配"不撑爆"目标，且 95 分位是容量工程的行业标准（可省 30% 云成本）。**代价**：P95 略过度配置（安全余量）——容量治理允许的误差，换来稳定性。

### 1.6 为什么"告警是生命线绝不丢"

降噪的价值是"让值班看到该看的"，前提是"看到的都是真的"。如果 LLM 故障导致丢告警，就是**确定性事故**（值班没看到该看的），比降噪不足严重得多。所以所有降级路径都是"放行 + 粗糙处理"，绝不丢弃。这条纪律贯穿 v1（Kafka 故障直落审计）到 v8（混沌演练验证）。

### 2.2 `PlatformChatConfig.java`（统一 ChatClient：注册全部工具）

```java
package com.aiops.platform.config;

import com.aiops.platform.rca.ObservabilityTools;
import com.aiops.platform.rca.RunbookRetriever;
import com.aiops.platform.remediate.RemediationTools;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/**
 * 平台统一 ChatClient：注册 RCA 工具、处置工具、Runbook 检索工具。
 * 审批闸门（RemediationApprovalManager）作为 ToolCallingManager Bean 生效，
 * 对本 ChatClient 的处置工具调用自动拦截审批（[附录 05-SpringAI2-API基准/02 §1.3]）。
 * 本配置替换 [02-迭代一 §3.6] 的 ChatClientConfig 与 [04-迭代三 §4.7] 的
 * RemediationChatConfig（全平台只保留本一个 ChatClient Bean）。
 */
@Configuration
public class PlatformChatConfig {

    @Bean
    public ChatClient platformChatClient(ChatClient.Builder builder,
                                         ObservabilityTools observabilityTools,
                                         RemediationTools remediationTools,
                                         RunbookRetriever runbookRetriever) {
        return builder
                .defaultTools(observabilityTools, remediationTools, runbookRetriever)
                .build();
    }
}
```

## 3. 最容易写错的五处

| # | 位置 | 错误 | 后果 | 正确 |
|---|------|------|------|------|
| 1 | L3 门控 | 全量告警过 LLM | 成本爆炸 | 级联预过滤（≥3 条或含 critical 才 LLM） |
| 2 | HITL 落点 | 写在 Advisor | 拦不到工具执行 | ToolCallingManager 装饰器 |
| 3 | 长任务 | 只把状态落库、无恢复循环 | 进程一死 run 就死 | Checkpoint 恢复循环（教程 40） |
| 4 | 知识检索 | 纯向量 | 关键参数不同误召回 | 混合检索（FTS+向量+RRF）+ citation |
| 5 | 降级 | 全局 fail-open | 告警丢失 | 告警 fail-open（绝不丢）、审计 fail-close |
