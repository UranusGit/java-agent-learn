# 06-路由灰度与秒级回滚

> **定位**：让"改路由参数"从**高危操作**变成**可灰度、可回滚**的日常操作。核心三件套：**① 路由配置与代码解耦**（阈值/示例句/意图存配置中心）② **灰度切流**（新路由配置只对 10% 流量生效，对比误分率）③ **秒级回滚**（配置版本回退预案）。呼应 [62-灰度发布与版本管理](../../教程/04-企业级架构主干/09-灰度发布与版本管理.md)。前置阅读：[05-命中率优化与按意图阈值](05-命中率优化与按意图阈值.md)。
>
> **铁律 0**：路由配置序列化到 DB/配置中心（自研「概念代码」）；不引入未实证 API。

## 一、四问

| 问 | 答 |
|----|----|
| **新增了什么需求** | ①RouteConfig 版本化 + 存储到配置中心 ②灰度切流（按租户/按流量百分比）③同版本 A/B 对比命中/误分 ④回滚预案 |
| **影响了哪些模块** | RouteConfig → 数据源化/版本化；SemanticRouter → 读配置版本；新增 灰度切流器 + 版本切换 |
| **架构如何演进** | 路由参数从"改代码发版"演进为"改配置 + 灰度 + 回滚" |
| **上一版痛点** | 改阈值要发版；全量上线误分事故只能 git revert + 全量重发 |

**本迭代验收**：①配置变更通过配置中心热更新，无需发版 ②灰度 10% 对比误分率，达标才放大 ③任何版本可秒级回滚，回滚后误分率恢复基线。

## 二、配置版本化 + 灰度

```json
{
  "configVersion": "v12",
  "base": { "scenario": "cn_order" },
  "intentThresholds": {
    "APPROVAL": 0.85, "RAG": 0.60, "ORDER": 0.60, "DATA": 0.75
  },
  "rollout": { "percentage": 10, "byTenantGroup": ["beta-group"] }
}
```

```java
// 概念代码：按流量/租户灰度切流
public RouteConfig activeConfig(String tenantId) {
    RouteConfig v = routeConfigStore.latest();
    if (matchesRollout(v, tenantId)) return v;         // 命中灰度 → 用新配置
    return routeConfigStore.version(v.baseVersion());   // 否则 → 用基线路由
}
```

**灰度观测**：对比灰度组 vs 对照组在 04 迭代指标上的**误分率是否恶化**，配对校验（呼应 [附录 12/03](../../附录/11-评估与可观测生态/03-在线实验与AB统计.md)），不达阈值不放量。

### 二.1 本节测试与验证（配置版本化 + 灰度切流）

**前置条件**：`routeConfigStore` 已接入（DB/配置中心）；`activeConfig(tenantId)` 与 `matchesRollout` 已实现。

**材料——灰度配置示例**：

```json
{ "configVersion": "v12", "rollout": { "percentage": 10, "byTenantGroup": ["beta-group"] } }
```

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 配置中心改阈值并发布 v12 | 无需发版，热更新后 P95 生效 ≤ 2s（验收①与 10 的 P95 口径一致前置） |
| 2 | 用 beta-group 租户请求 | 命中的灰度 → 走新配置 v12（`matchesRollout` 命中） |
| 3 | 用非 beta 租户请求 | 走基线路由配置（`version(baseVersion)`） |
| 4 | 对比灰度/对照两组误分率 | 配对校验，误分率未恶化则不放大（验收②） |

**失败排查**：①beta 组没走新配置→`matchesRollout` 租户判定未命中；②非 beta 也被灰度→version 回退逻辑缺失；③生效慢→配置中心拉取间隔或版本协商未做（10 深化）。

## 三、秒级回滚

```mermaid
graph TB
    A["灰度/全量后<br/>误分率上升"] --> B{"超标?"}
    B -->|"是"| C["一键切回<br/>上一个configVersion"]
    B -->|"否"| D["继续放量"]
    C --> E["误分样本归因<br/>是阈值/示例句哪个问题"]
    C --> F["修复后重新灰度"]
    style C fill:#ffcdd2
```

**要点**：配置必须保留版本历史 + 支持回退到任意历史版本；回滚本身也是"配置切换"（秒级生效），区别于"代码回滚"（需重发）。

### 三.1 本节核对（秒级回滚）

- [ ] "误分率超标 → 一键切回上一 configVersion → 归因 → 修复重灰度"流程能复述，与 §二 灰度衔接无断裂
- [ ] 能说清"配置回滚（秒级）vs 代码回滚（需重发）"的差异，与正文口径一致

## 四、全篇回归验证

| 测试 | 期望 |
|------|------|
| 改阈值 | 配置中心热更新，10s 生效 |
| 灰度 10% | 仅 beta 组用新配置，误分率可对比 |
| 误分恶化 | 一键回滚 v12，误分率恢复 |
| 版本历史 | 可查所有 configVersion 变更记录 |

**回归断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 配置中心改阈值 | 10s 内热更新生效，无需发版（对应上表首行） |
| 2 | 只发 v12 给 beta 组 | 仅 beta 组用新配置，误分率可与对照组对比（对应上表次行） |
| 3 | 制造误分率恶化 | 一键回滚 v12，误分率恢复基线；所有 configVersion 变更记录可查（对应上表后两行） |

**回归失败排查**：①热更新不生效→发布管道未监听变更或缺版本协商；②回滚不了→历史版本未保留；③版本记录查不到→审计落库未实现（09 承接）。
