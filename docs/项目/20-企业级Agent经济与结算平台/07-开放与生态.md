## 二、商店分润（一次调用的钱怎么分）

```mermaid
sequenceDiagram
    participant B as 买方Agent
    participant MKT as market-svc
    participant LED as 账本(04)
    participant A as 能力作者
    B->>MKT: 调用上架能力(带委托凭证)
    MKT->>MKT: 授权闸(02)+预授权
    MKT->>LED: CAPTURE ¥1.0(币种+汇率快照)
    LED->>LED: 分润事件:作者0.7/平台0.2/渠道0.1
    Note over LED: ∑分润 == 收入(硬不变式)
    LED-->>A: 结算周期到账
```

**上架门槛**：能力必须挂评估凭证（外部信任分）——生态里"敢卖"与"敢买"对称：卖方过质量闸，买方过授权闸。第三方信任凭证的互认协议属外部依赖（本平台预留接口，见 13-前沿生态方向讨论）。

### 二.1 本节核对（商店分润）

- [ ] 一次调用链路（授权闸→预授权→CAPTURE→分润事件→三方到账）能在序列图上说清；"∑分润==收入"是硬不变式
- [ ] 上架门槛"卖方过质量闸、买方过授权闸"的对称逻辑能复述，第三方凭证互认标注为外部依赖（非本平台实现）

### 二.2 本节测试与验证（分润三方到账平衡）

**前置条件**：CAPTURE→分润事件链（0.7/0.2/0.1）可跑 junit。

**材料 A——分润平衡测试**（junit）：

```java
@Test void 百次调用三方分润总账平() {
    for (int i = 0; i < 100; i++) market.capture(buyer, capability, amt("1.0"), snapshotUsd());
    Money income   = ledger.sumByType(REVENUE);
    Money author   = ledger.sumBySplit(AUTHOR);
    Money platform = ledger.sumBySplit(PLATFORM);
    Money channel  = ledger.sumBySplit(CHANNEL);
    assertEquals(0, income.compareTo(author.add(platform).add(channel)));  // ∑分润==收入
    assertEquals(0, author.compareTo(amt("70.0")));                        // 逐笔+汇总双验证
}
```

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 材料 A 用例 | 全绿；∑分润==收入恒等式成立（逐笔+汇总双验证） |
| 2 | 逐笔抽查 1 条 CAPTURE | 分润事件三向比例 0.7/0.2/0.1，各带汇率快照字段 |
| 3 | 上架门槛核对 | 无评估凭证的能力上架被拒（卖方质量闸生效） |

**失败排查**：①恒等式破→费率小数精度（整数 micro 运算，§五 纪律）；②无评估凭证也上架→上架校验未接信任分源。

## 三、汇率快照纪律

- 入账事件携带 `(amount, currency, rate, rateAt)` 四元组，**报表层永远用快照汇率**——"月末按最新汇率重算"是财务对账的头号灾难源。
- 本位币唯一：内部总账只有一种本位币，外币交易全部在事件层换算入账。

### 三.1 本节核对（汇率快照纪律）

- [ ] 事件携带 `(amount, currency, rate, rateAt)` 四元组、报表层永远用快照汇率——"月末按最新汇率重算"是规避的对账灾难
- [ ] 内部总账唯一本位币，外币在事件层换算，理解其与 §一 验收②（月末不翻账）的关联

### 三.2 本节测试与验证（快照入账月末不翻账）

**前置条件**：入账事件四元组（amount/currency/rate/rateAt）落库；报表层可重算。

**材料 B——汇率波动对照测试**（junit）：

```java
@Test void 月末重算金额不随行情变() {
    Money atDeal = ledger.report(month("2026-08"), FX_MODE.SNAPSHOT);   // 成交时刻快照
    fxMarket.move("USD/CNY", 7.10, 7.35);                              // 月末行情波动 3.5%
    Money after  = ledger.report(month("2026-08"), FX_MODE.SNAPSHOT);  // 再出一次报表
    assertEquals(0, atDeal.compareTo(after));                          // 分毫不差
    SpendEntry e = ledger.firstForeignEntry();
    assertNotNull(e.rateAt());                                         // 四元组齐全可回溯
}
```

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 材料 B 用例 | 全绿；行情波动前后报表金额一致（快照入账） |
| 2 | 抽查事件四元组 | `(amount, currency, rate, rateAt)` 全部非空 |
| 3 | 本位币核对 | 内部总账单一本位币；外币仅存在于事件层 |

**失败排查**：①金额变了→报表层读了实时汇率（必须锁 SNAPSHOT 模式）；②rateAt 缺失→入账组装时未带成交时刻（事后补汇率=翻账灾难源）。

### 四.2 本节测试与验证（仲裁分流与冻结）

**前置条件**：争议受理→一级自动比对→升级链→冻结闸可跑 junit。

**材料 C——争议分流测试**（junit）：

```java
@Test void 证据清晰自动裁决_冲突升级_冻结贯穿() {
    // 证据清晰：双方计量一致但 SLA 未达 → 一级自动裁决复用 06 折扣规则
    Dispute d1 = dispute(logs(matching()), sla(breached()));
    assertEquals(L1_AUTO, d1.level());
    assertEquals(REFACTION.DISCOUNT, d1.execute());
    // 证据冲突：买方日志与计量事件对不上 → 升级二级（平台裁决）
    Dispute d2 = dispute(logs(conflicting()), sla(ok()));
    assertEquals(L2_PLATFORM, d2.level());
    // 冻结贯穿：d2 仲裁期间款项不可动（支付闸拒绝划付）
    assertThrows(FrozenFundsException.class, () -> ledger.payout(d2.amount()));
    assertTrue(d2.frozenAmount().compareTo(d2.amount()) == 0);
}
```

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 材料 C 用例 | 全绿；分流（自动裁决/升级）与 §四 图一致 |
| 2 | 仲裁期间尝试划付 | 冻结闸拒绝（款项不可动） |
| 3 | 终裁后执行 | 退款/折价/驳回落账并与冻结金额对平 |

**失败排查**：①冻结失效→争议状态未接支付闸（§五 纪律）；②一级误升级→证据比对把"日志时区差"判为冲突（比对前先归一时区）。
