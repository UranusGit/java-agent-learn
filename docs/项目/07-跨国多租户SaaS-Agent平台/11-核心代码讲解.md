## 1. 七个关键设计复盘

### 1.1 为什么隔离是"schema 隔离 + 事务级 RLS"双层（本项目最痛的教训）

v2 第一版实现"新建连接 `SET app.current_tenant` 后归还"——连接级（session 级）设置在连接池下对后续借出的业务连接毫无作用，且污染池中连接导致**反向串号**，越权压测全泄露。修正为两条：

1. **schema-per-tenant**：每租户一个独立 schema（`t_<id>`），业务表物理隔离——删档=`DROP SCHEMA`、导出=只读该 schema、迁移=只迁该 schema。
2. **事务级 RLS**：事务开头 `set_config('search_path', 't_<id>', true)` + `set_config('app.current_tenant', '<id>', true)`（第三参 true = SET LOCAL 语义，随事务结束失效，连接归还池无残留），配合 `FORCE ROW LEVEL SECURITY`——即使 search_path 被注入或跨 schema 全限定查询，RLS 也兜底为 0 行。

**泛化教训**：任何"连接级状态"在连接池环境下都是错的——状态要么事务级（随事务生死），要么显式传参。识别这类错误的方法只有一个：**越权测试矩阵进 CI（ADR-207）**，因为 code review 看不出"SET 了但没用"。

### 1.2 为什么配额是"预扣+修正"而不是实时扣

实时逐 token 扣减的 Redis QPS 与对话流量同阶（每秒数千次），且流式中途断连时扣多少算不清。预扣（请求开始按估计量原子扣）+ 修正（完成回补差额）把 Redis 压力降为每请求 2 次，且天然覆盖断连场景（预扣已收，实际按已有 usage 修正）。**代价**：短暂超限窗口（预扣估计偏低时）——配额治理允许的误差换架构简洁，商业上完全可接受。

### 1.3 为什么账单不能从指标出（ADR-214）

Prometheus 指标的三宗罪：可重置（重启丢基数）、可降采样（聚合丢明细）、无审计语义（谁都不能对指标数发誓）。计费数据的要求恰好相反。所以**事件流水（append-only，DB 触发器拒绝 UPDATE/DELETE）是账单唯一数据源，指标只管运维**——两类数据的不同命运在设计期就要分轨。

### 1.4 为什么灰度原子单位是租户（ADR-217）

SaaS 的体验一致性单元是"企业"不是"用户"：同一公司两个员工看到的 Agent 一个聪明一个笨，工单必然产生且无法解释。对比：To C 产品灰度按用户分桶完全正常。**灰度粒度=产品的信任一致性单元**，这是产品形态决定的，没有技术对错。

### 1.5 为什么 TTFT 进 SLI（ADR-220）

对话产品的"可用"包含"及时"。如果 SLI 只有成功率，8 秒首字延迟的系统也能 100% 达标——但客户会流失。SLI 的选择暴露的是产品理解：批处理产品用吞吐、交易产品用成功率与一致性、对话产品必须含延迟。**SLO 设计是产品知识，不是运维知识**。

### 1.6 为什么 DR 不跨境（ADR-230）

驻留承诺与容灾冗余的矛盾是真实的架构张力。答案不是"技术上做不到"，而是**风险排序**：违约的合同罚金+监管处罚+信任崩塌是确定性损失；区域级故障是概率事件且 RTO 内可部分恢复。所以法域内找备区，找不到就降级方案+书面披露——架构师的诚实就是把不可兼得的东西明码标价给业务方选。

### 1.7 为什么计费三副本对账（ADR-215）

单点计量必然有误差（断连、重试、并发窗口）。三副本（原始事件/配额流水/供应商账单）互相对账，把"账单对不对"从"我们系统说是多少"变成"三个独立来源一致"——对不上的**冻结不出账、人工裁定后留痕**。错账的信任代价远高于晚出账。

### 2.2 本节测试与验证（六处易错点复现验证）

**前置条件**：应用以 `mvn spring-boot:run -Dspring-boot.run.profiles=saasagent` 运行（端口 8081，见 [00] 基线配置）；psql 可连业务库（`$DATABASE_URL` 走 `.env`，不落明文）；第 4/5/6/7 项为纯运行时断言，无需造数据。

**材料**：

```bash
# 材料①：复现 v1 错误写法——连接级 SET 在事务间残留（§2 表第 1 项的反向串号根源）
psql "$DATABASE_URL" -c "
SET app.current_tenant = '<acme-uuid>';                -- 连接级（错误）
BEGIN; SELECT current_setting('app.current_tenant', true); COMMIT;   -- 事务内仍可见
BEGIN; SELECT current_setting('app.current_tenant', true); COMMIT;   -- 第二个事务仍可见 = 污染残留"

# 材料②：正确写法——事务级 set_config 第三参 true（SET LOCAL），事务外零残留
psql "$DATABASE_URL" -c "
BEGIN;
SELECT set_config('search_path', 't_acme', true);
SELECT set_config('app.current_tenant', '<acme-uuid>', true);
SELECT count(*) FROM conversation;                     -- RLS 生效：只见 acme 的行
COMMIT;
SELECT current_setting('app.current_tenant', true);    -- 事务外：空（连接归池零残留）"

# 材料③：双绑缺一——只绑 search_path、漏绑 current_tenant（§2 表第 2 项）
psql "$DATABASE_URL" -c "
BEGIN;
SELECT set_config('search_path', 't_acme', true);
SELECT count(*) FROM conversation;                     -- FORCE RLS 下无租户值
COMMIT;"

# 材料④：越权响应（§2 表第 4 项）——租户 A 的 token 访问租户 B 的会话
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  "http://localhost:8081/conversations/<租户B会话ID>/messages" \
  -H "Authorization: Bearer <租户A的TOKEN>" -H "Content-Type: application/json" \
  -d '{"content":"hi"}'
```

**步骤与断言**：

| # | 易错点 | 操作 | 预期断言 |
|---|--------|------|---------|
| 1 | 连接级 SET 污染 | 材料① | 两个事务都能读到租户值（残留复现——连接池下这就是反向串号的根源） |
| 2 | 事务级绑定零残留 | 材料② | 事务内 count 只含 acme 行；事务外 `current_setting(..., true)` 返回空（SET LOCAL 随事务失效） |
| 3 | 双绑缺一 | 材料③ | 0 行（若该自定义参数从未在本会话设置过，`current_setting` 直接报错——同样算复现成立：漏绑即不可用） |
| 4 | Lua 原子扣 | 复用 [03 §3.9.1] 步骤 4 | 1000 并发 `preCharge` 成功次数 ≤ 1000，零超卖 |
| 5 | 越权 404 | 材料④ | 输出 `404`（不是 403——不暴露资源存在性，ADR-206） |
| 6 | 双层限流 | 复用 [03 §3.9.1] 步骤 5 | 第 6 个并发会话 429 + Retry-After（并发层先于 Token 层触发） |
| 7 | fencing 防脑裂 | 复用 [10] 篇 DR 演练断言 | 旧主写入被 fencing token 拒绝（人工决策 + fencing 优先于自动切换） |

**失败排查**：材料②事务外仍读到值 → 第三参漏传 `true`（写成了会话级 `set_config(..., false)`，等价于 v1 错误写法）；材料④返回 403 → 异常映射把"不存在"翻译成了"禁止"（泄露资源存在性）；材料③查到了行 → `FORCE ROW LEVEL SECURITY` 未对该表启用（RLS 策略存在但对表属主不生效）。
