# 项目 07：跨国多租户 SaaS Agent 平台 — 02-迭代一：多租户数据隔离（schema 隔离 + 事务级 RLS 硬边界）

> **定位**：把 tenant_id 从"躺在表里的列"升级为**双层硬隔离**——① **schema-per-tenant**：每个租户一个独立 schema，业务表物理隔离；② **事务级 RLS**：`set_config(..., true)`（SET LOCAL 语义）绑定当前租户，FORCE RLS 兜底"漏写 where 也安全"。含早期错误方案（连接即关的 SET）的检讨与修正。本文给出**完整可手写代码**（一行不省略）。
>
> 「遇到阻塞？→ [教程 26-多租户隔离与资源治理 §数据层隔离与 RLS]、[教程 42-响应式错误处理 §Context 传递]；API 真实性以 [附录 05-SpringAI2-API基准] 为准」

## 1. 四问

| 问 | 答 |
|----|----|
| **新增了什么需求** | ① 租户注册即建独立 schema（schema 隔离）② 数据访问事务级绑定当前租户 ③ 每租户 schema 内 RLS 强制兜底 ④ 越权测试矩阵进 CI |
| **影响了哪些模块** | 身份服务（注册时调 TenantProvisioner）、全部数据访问仓库（继承 TenantScopedRepository）、AgentChatService（对话链路在事务内） |
| **架构如何演进** | 单 schema（public 全表）→ **public 只留身份/控制数据 + `t_<id>` 每租户 schema 存业务数据**；连接级 SET（错误）→ 事务级 set_config（正确） |
| **上一版痛点是什么** | 隔离靠代码自觉（where tenant_id=?），第二家租户理论上可通过会话 ID 探测第一家数据（越权读写） |

## 2. 需求与上一版痛点

| v1 痛点 | 对策 |
|---------|------|
| 隔离靠代码自觉（where tenant_id=?） | schema 隔离（物理边界）+ RLS（数据库层强制，漏写 where 也安全） |
| 理论上可探测他租户数据 | 越权测试矩阵进 CI（ADR-207） |
| 应用层漏绑租户 = 数据泄露 | 事务级绑定 + FORCE RLS，fail-closed |

## 3. 隔离方案选型

| 方案 | 隔离强度 | 运维成本 | 千级租户可扩展 | 本项目结论 |
|------|---------|---------|---------------|-----------|
| 代码自觉 where | ❌ 无强制 | 低 | - | 弃（v1 现状） |
| 共享 schema + 仅 RLS | ✅ DB 强制 | 中 | ✅ | 覆盖不足——租户删档/数据导出/驻留迁移都需要 schema 级边界，RLS 单独兜不住"整租户生命周期"操作 |
| **schema-per-tenant + 事务级 RLS** | ✅✅ schema 硬边界 + RLS 纵深 | 中高（迁移自动跑 N 次） | ✅ | **采用**（ADR-201 修正） |
| 独立库 per-tenant | ✅✅✅ | 极高 | ❌ | 弃（Enterprise 驻留用"区域分区"另 covers） |

**为什么 schema 隔离 + RLS 双层**：schema 解决"租户生命周期"（删档 = DROP SCHEMA；导出 = 只读该 schema；迁移 = 只迁该 schema）；RLS 解决"同一 schema 内的行级越权 + search_path 注入/跨 schema 全限定查询兜底"。两者互补，不是二选一。

## 4. 关键实现

### 4.1 每租户 schema 的 DDL（`db/tenant-schema.sql`）

```sql
-- 每租户独立 schema 的建表脚本。TenantProvisioner 在注册时对每个租户执行一次。
-- 表 owner 是应用 DB 角色；RLS 用 FORCE——表 owner 也受约束（绕过应用的直连也读不到他租户）。

CREATE TABLE conversation (
    id         UUID PRIMARY KEY,
    tenant_id  UUID NOT NULL,
    user_id    UUID NOT NULL,
    agent_id   UUID,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE message (
    id              UUID PRIMARY KEY,
    tenant_id       UUID NOT NULL,
    conversation_id UUID NOT NULL,
    role            TEXT NOT NULL,          -- user | assistant | tool
    content         TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE document_chunk (                -- PgVector 向量库，随主库复制（v8 区域复制）
    id            UUID PRIMARY KEY,
    tenant_id     UUID NOT NULL,
    content       TEXT NOT NULL,
    embedding     vector(1536),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ===== 纵深：RLS（即使 search_path 被注入/跨 schema 全限定查询也兜底）=====
ALTER TABLE conversation ENABLE ROW LEVEL SECURITY;
ALTER TABLE conversation FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON conversation
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

ALTER TABLE message ENABLE ROW LEVEL SECURITY;
ALTER TABLE message FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON message
    USING (tenant_id = current_setting('app.current_tenant')::uuid);

ALTER TABLE document_chunk ENABLE ROW LEVEL SECURITY;
ALTER TABLE document_chunk FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON document_chunk
    USING (tenant_id = current_setting('app.current_tenant')::uuid);
```

### 4.2 租户注册：`TenantProvisioner.java`（schema 隔离的落地）

```java
package com.acme.saas.tenant;

import org.springframework.r2dbc.core.DatabaseClient;   // ⚠ 需引入依赖 org.springframework.boot:spring-boot-starter-data-r2dbc（本地未下载，未 javap 实证；以引入依赖后 javap 输出为准）
import org.springframework.stereotype.Component;
import reactor.core.publisher.Mono;

import java.util.UUID;

/**
 * 租户注册时创建独立 schema + 建表 + 开 RLS。
 * schema 名稳定映射自 tenantId（可逆，跨区域复制时保持同构）。
 */
@Component
public class TenantProvisioner {

    private final DatabaseClient db;

    public TenantProvisioner(DatabaseClient db) {
        this.db = db;
    }

    public Mono<Void> provision(UUID tenantId) {
        String schema = schemaName(tenantId);
        return createSchema(schema)
                .then(createConversation(schema))
                .then(createMessage(schema))
                .then(createDocumentChunk(schema))
                .then(enableRls(schema))
                .then();
    }

    public static String schemaName(UUID tenantId) {
        return "t_" + tenantId.toString().replace("-", "");
    }

    private Mono<Long> createSchema(String schema) {
        return db.sql("CREATE SCHEMA IF NOT EXISTS " + schema).fetch().rowsUpdated();
    }

    private Mono<Long> createConversation(String schema) {
        return db.sql("""
                CREATE TABLE IF NOT EXISTS %s.conversation (
                    id         UUID PRIMARY KEY,
                    tenant_id  UUID NOT NULL,
                    user_id    UUID NOT NULL,
                    agent_id   UUID,
                    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
                )
                """.formatted(schema)).fetch().rowsUpdated();
    }

    private Mono<Long> createMessage(String schema) {
        return db.sql("""
                CREATE TABLE IF NOT EXISTS %s.message (
                    id              UUID PRIMARY KEY,
                    tenant_id       UUID NOT NULL,
                    conversation_id UUID NOT NULL,
                    role            TEXT NOT NULL,
                    content         TEXT NOT NULL,
                    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
                )
                """.formatted(schema)).fetch().rowsUpdated();
    }

    private Mono<Long> createDocumentChunk(String schema) {
        return db.sql("""
                CREATE TABLE IF NOT EXISTS %s.document_chunk (
                    id         UUID PRIMARY KEY,
                    tenant_id  UUID NOT NULL,
                    content    TEXT NOT NULL,
                    embedding  vector(1536),
                    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
                )
                """.formatted(schema)).fetch().rowsUpdated();
    }

    private Mono<Long> enableRls(String schema) {
        // FORCE：表 owner 也受 RLS 约束——绕过应用的直连同样读不到他租户数据
        return db.sql("""
                ALTER TABLE %s.conversation ENABLE ROW LEVEL SECURITY;
                ALTER TABLE %s.conversation FORCE ROW LEVEL SECURITY;
                ALTER TABLE %s.message ENABLE ROW LEVEL SECURITY;
                ALTER TABLE %s.message FORCE ROW LEVEL SECURITY;
                ALTER TABLE %s.document_chunk ENABLE ROW LEVEL SECURITY;
                ALTER TABLE %s.document_chunk FORCE ROW LEVEL SECURITY
                """.formatted(schema, schema, schema, schema, schema, schema))
                .fetch().rowsUpdated();
    }
}
```

> 生产环境多个 `;` 语句在部分 R2DBC 驱动下需逐条执行——本文按 PostgreSQL R2DBC 支持多语句脚本写（驱动对 `;` 分句），若你的驱动报错，把 `enableRls` 拆成 6 个 `.then()` 链即可。RLS 策略（`CREATE POLICY ... USING`）在 4.1 的 `tenant-schema.sql` 里与建表一并执行，属表定义的一部分。

### 4.3 事务级绑定：连接级 SET 的错误检讨与修正

> **早期错误方案**（本迭代第一版实现，检讨保留）：新建 Connection 执行 `SET app.current_tenant = 'x'` 后立即归还连接——**对池中后续借出的业务连接毫无作用，且 session 级 SET 会污染连接池**：归还后该连接被下一个租户借出，`app.current_tenant` 仍是上一个租户的值，RLS 形同虚设甚至反向串号。压测越权测试时全部泄露，教训沉痛。

**修正方案：事务级 `set_config(..., true)` + 事务内绑定**

```java
package com.acme.saas.tenant;

import org.springframework.r2dbc.core.DatabaseClient;   // ⚠ 需引入依赖 org.springframework.boot:spring-boot-starter-data-r2dbc（本地未下载，未 javap 实证；以引入依赖后 javap 输出为准）
import org.springframework.stereotype.Component;
import reactor.core.publisher.Mono;

import java.util.UUID;

/**
 * 事务级租户绑定。在事务开头把 search_path 与 app.current_tenant 都设为
 * 当前租户，set_config 第三参 true = 事务级（等价 SET LOCAL）——
 * 事务结束自动失效，连接归还池无残留，不会串号。
 */
@Component
public class TenantRlsBinder {

    private final DatabaseClient db;

    public TenantRlsBinder(DatabaseClient db) {
        this.db = db;
    }

    public Mono<Void> bind(UUID tenantId) {
        String schema = TenantProvisioner.schemaName(tenantId);
        return db.sql("SELECT set_config('search_path', :schema, true)")
                .bind("schema", schema)
                .fetch().one()
                .then(db.sql("SELECT set_config('app.current_tenant', :tenantId, true)")
                        .bind("tenantId", tenantId.toString())
                        .fetch().one())
                .then();
    }
}
```

**为什么事务级绑定是正确答案**：
- 事务结束 `set_config(..., true)` 自动失效 → 连接归还池后无残留（无污染）；
- 同一连接的下一个租户事务重新绑定 → 无串号；
- 连接池任何异步归还时序都不影响（绑定与业务操作在同一事务、同一连接）；
- `search_path` 与 `current_tenant` 一起绑：前者让业务表解析到租户 schema，后者喂 RLS 策略。

### 4.4 数据访问基类：`TenantScopedRepository.java`

```java
package com.acme.saas.tenant;

import org.springframework.transaction.reactive.TransactionOperator;
import reactor.core.publisher.Mono;

import java.util.UUID;

/**
 * 数据访问基类：所有租户业务数据事务的固定开头。
 * 业务代码不写 tenant_id 条件——隔离全在这层 + DB 层。
 */
public abstract class TenantScopedRepository {

    private final TransactionOperator tx;
    private final TenantRlsBinder binder;

    protected TenantScopedRepository(TransactionOperator tx, TenantRlsBinder binder) {
        this.tx = tx;
        this.binder = binder;
    }

    /** 事务内先绑租户，再执行业务操作；绑定随事务结束失效。 */
    protected <T> Mono<T> inTenantScope(UUID tenantId, Mono<T> operation) {
        return tx.transactional(binder.bind(tenantId).then(operation));
    }
}
```

### 4.5 仓库改造示例：`MessageRepository.java`（v1 → v2）

```java
package com.acme.saas.conversation;

import com.acme.saas.tenant.TenantRlsBinder;
import com.acme.saas.tenant.TenantScopedRepository;
import org.springframework.r2dbc.core.DatabaseClient;   // ⚠ 需引入依赖 org.springframework.boot:spring-boot-starter-data-r2dbc（本地未下载，未 javap 实证；以引入依赖后 javap 输出为准）
import org.springframework.stereotype.Repository;
import org.springframework.transaction.reactive.TransactionOperator;
import reactor.core.publisher.Mono;

import java.time.Instant;
import java.util.UUID;

@Repository
public class MessageRepository extends TenantScopedRepository {

    private final DatabaseClient db;

    public MessageRepository(DatabaseClient db, TransactionOperator tx, TenantRlsBinder binder) {
        super(tx, binder);
        this.db = db;
    }

    /** 业务代码不写 tenant_id 条件；search_path 已由事务级绑定指向本租户 schema。 */
    public Mono<Void> insert(UUID tenantId, UUID conversationId, String role, String content) {
        return inTenantScope(tenantId, db.sql("""
                INSERT INTO message (id, tenant_id, conversation_id, role, content, created_at)
                VALUES (:id, :tenantId, :conversationId, :role, :content, :createdAt)
                """)
                .bind("id", UUID.randomUUID())
                .bind("tenantId", tenantId)
                .bind("conversationId", conversationId)
                .bind("role", role)
                .bind("content", content)
                .bind("createdAt", Instant.now())
                .then());
    }

    public Mono<Long> countByConversation(UUID tenantId, UUID conversationId) {
        return inTenantScope(tenantId, db.sql(
                        "SELECT count(*) FROM message WHERE conversation_id = :cid")
                .bind("cid", conversationId)
                .map((row, meta) -> row.get(0, Long.class))
                .one());
    }
}
```

`AgentChatService.java` 无需改业务逻辑——`messages.insert(...)` 内部已走 `inTenantScope`，对话链路自动获得隔离：

```java
package com.acme.saas.agent;

import com.acme.saas.conversation.MessageRepository;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.memory.ChatMemory;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import java.util.UUID;

@Service
public class AgentChatService {

    private final ChatClient chatClient;
    private final MessageRepository messages;

    public AgentChatService(ChatClient chatClient, MessageRepository messages) {
        this.chatClient = chatClient;
        this.messages = messages;
    }

    public Flux<String> chat(UUID tenantId, UUID userId, UUID conversationId, String message) {
        StringBuilder acc = new StringBuilder();
        return messages.insert(tenantId, conversationId, "user", message)
                .thenMany(chatClient.prompt()
                        .user(message)
                        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId.toString()))
                        .stream()
                        .content()
                        .doOnNext(acc::append))
                .concatWith(Mono.defer(() ->
                        messages.insert(tenantId, conversationId, "assistant", acc.toString())));
    }
}
```

### 4.6 纵深：隔离不是单点防线

| 防线 | 机制 |
|------|------|
| ① JWT 解析出 tenantId（TenantContextFilter） | 不可伪造（签名 + 过期校验） |
| ② API 层：资源属主校验（conversation 属于该租户？） | 返回 404 而非 403（ADR-206） |
| ③ DB 层：schema 隔离 | 每个租户的业务表物理隔离（search_path 事务级指向） |
| ④ DB 层：RLS 强制兜底 | 漏写 where / search_path 注入 / 跨 schema 全限定查询都读不到他租户行 |

**向量检索的第四道防线**：PgVector 的 `document_chunk` 随主库复制，检索用 `SearchRequest.builder().filterExpression("tenant_id == '<id>'")` 做元数据过滤 + RLS 双保险（[教程 06-向量数据库 §过滤]）。

### 4.7 越权测试矩阵（进 CI）

```java

import com.acme.saas.identity.Plan;

import com.acme.saas.tenant.TenantProvisioner;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;   // ⚠ 需引入依赖 org.springframework.boot:spring-boot-starter-test（本地未下载，未 javap 实证；以引入依赖后 javap 输出为准）
import org.springframework.r2dbc.core.DatabaseClient;   // ⚠ 需引入依赖 org.springframework.boot:spring-boot-starter-data-r2dbc（本地未下载，未 javap 实证；以引入依赖后 javap 输出为准）
import org.springframework.test.web.reactive.server.WebTestClient;   // ⚠ 需引入依赖 org.springframework.boot:spring-boot-starter-test（本地未下载，未 javap 实证；以引入依赖后 javap 输出为准）
import reactor.core.publisher.Mono;
import reactor.test.StepVerifier;   // ⚠ 需引入依赖 io.projectreactor:reactor-test（本地未下载，未 javap 实证；以引入依赖后 javap 输出为准）

import java.util.UUID;

import static org.assertj.core.api.Assertions.assertThat;

/**
 * 越权测试矩阵：全数据访问接口 × 越权场景，CI 必跑（ADR-207）。
 * 识别"SET 了但没用"这类 code review 看不出的隔离回归，只能靠矩阵。
 */
@SpringBootTest
class TenantIsolationTest {

    @Autowired WebTestClient web;
    @Autowired DatabaseClient db;
    @Autowired TenantRlsBinder binder;

    @Test
    void tenantBCannotReadTenantAConversation() {
        UUID tenantA = register("Acme", "a@acme.com");
        UUID tenantB = register("Globex", "b@globex.com");
        String tokenA = login("a@acme.com");
        String tokenB = login("b@globex.com");
        String convId = createConversation(tokenA);

        // B 用 A 的会话 ID 读 → 404 而非 403（不暴露存在性，ADR-206）
        web.get().uri("/conversations/{id}", convId)
                .header("Authorization", "Bearer " + tokenB)
                .exchange()
                .expectStatus().isNotFound();
    }

    @Test
    void crossSchemaQueryWithoutMatchingTenantIsBlockedByRls() {
        UUID tenantA = register("Acme", "a@acme.com");
        UUID tenantB = register("Globex", "b@globex.com");
        insertMessageForTest(tenantA);

        // 模拟 search_path 注入/跨 schema 全限定查询：绑定 B，但读 A 的 schema
        // RLS 策略要求 tenant_id = current_tenant(B)，而 t_A 行全是 A → 0 行
        StepVerifier.create(countInSchemaAsTenant(tenantB, TenantProvisioner.schemaName(tenantA)))
                .assertNext(n -> assertThat(n).isZero())
                .verifyComplete();
    }

    private Mono<Long> countInSchemaAsTenant(UUID currentTenant, String targetSchema) {
        return binder.bind(currentTenant)
                .then(db.sql("SELECT count(*) FROM " + targetSchema + ".message")
                        .map((row, meta) -> row.get(0, Long.class))
                        .one());
    }

    private void insertMessageForTest(UUID tenantId) {
        binder.bind(tenantId).block();
        db.sql("""
                INSERT INTO message (id, tenant_id, conversation_id, role, content, created_at)
                VALUES (:id, :tenantId, :convId, 'user', 'hello', now())
                """)
                .bind("id", UUID.randomUUID()).bind("tenantId", tenantId)
                .bind("convId", UUID.randomUUID())
                .then().block();
    }

    // —— 测试辅助：复用 /api/auth 注册登录、/conversations 建会话 ——
    private UUID register(String company, String email) {
        return web.post().uri("/api/auth/register")
                .bodyValue(new RegisterBody(company, email, "pw-123456"))
                .exchange().expectStatus().isOk()
                .returnResult(RegisterResponse.class).getResponseBody().blockFirst().tenantId();
    }

    private String login(String email) {
        return web.post().uri("/api/auth/login")
                .bodyValue(new LoginBody(email, "pw-123456"))
                .exchange().expectStatus().isOk()
                .returnResult(LoginResponse.class).getResponseBody().blockFirst().token();
    }

    private String createConversation(String token) {
        return web.post().uri("/conversations")
                .header("Authorization", "Bearer " + token)
                .exchange().expectStatus().isOk()
                .returnResult(ConversationResponse.class).getResponseBody().blockFirst().id();
    }

    record RegisterBody(String companyName, String adminEmail, String password) {}
    record RegisterResponse(UUID tenantId, UUID userId) {}
    record LoginBody(String email, String password) {}
    record LoginResponse(String token) {}
    record ConversationResponse(String id) {}
}
```

> 注：`binder.bind(...).block()` 出现在测试辅助方法里是可接受的——测试线程不是 Netty EventLoop，block 不违反 WebFlux 铁律（[教程 42-响应式错误处理 §6.1 为什么不能用 ThreadLocal]）。生产代码链路中绝不出现 `.block()`。
>
> `AuthContext` 在本测试未直接使用，属保留 import——真实越权矩阵还会验证"带 A 的 AuthContext 查 conversation 属主校验"用例，见 [11-核心代码讲解 §2]。

### 4.5 隔离生效可见（数据没串，看得见）

> 过程可见性是工业级标配（[附录 14/01-中间过程可见性设计]）。SaaS 多租户，用户最担心"我的数据会不会被别的租户看见"——隔离不是"默认不串，出事才排查"，而要让**每次跨租户访问尝试都可见**。隔离 execute emit 隔离事件：`{tenant, 访问目标, API归属性, 允许/拒绝, 理由}`。

| 要素 | 事件 | 使用者看到 |
|------|------|-----------|
| 归属校验 | TenantCheck{caller_tenant, target_ns}` | "租户A 访问 shared 命名空间" |
| 判定 | Allowed/Denied{rule}` | "越权→拒绝(数据层) " |
| 证明 | IsolationProof{row_count}` | "本次查询仅返回本租户 N 行" |

**四条纪律**：① **越权尝试必可见**——任何跨租户访问（即使被拦截）都发事件，用户/审计看到"尝试过、被拒了"，而不是"以为安全但无证据"；② **证明可见**——每次租户查询带"仅返回本租户 N 行"的证明，用户可核验隔离真实生效；③ 隔离事件与审计库（多租户审计）同源，合规方要能导出"租户A 从未见过租户B 数据"的证据；④ 事件不含标签外的数据内容（只给归属/计数，不给被拒内容的原文）。


## 5. 验收标准

| # | 验收项 | 标准 |
|---|--------|------|
| 1 | schema 隔离 | 每租户独立 schema，删租户 = DROP SCHEMA CASCADE（生命周期操作有边界） |
| 2 | RLS 强制 | 表 owner 直连（绕过应用）也无法跨租户读写（FORCE RLS 生效） |
| 3 | 越权矩阵 | 全接口 × 越权场景 0 泄露（CI 强制） |
| 4 | 无串号 | 500 并发混合租户事务，零串号（事务级绑定压测） |
| 5 | 业务无感 | Repository 业务代码不含 tenant_id 条件（隔离全在基类与 DB 层） |
| 6 | 存在性保护 | 越权访问返回 404 非 403 |

## 6. 本迭代的 ADR

| # | 决策 | 理由 |
|---|------|------|
| ADR-201（修正） | 池化多租户升级为 **schema-per-tenant + 事务级 RLS**，仍不做库级独享 | schema 给租户生命周期强边界（删档/导出/迁移），RLS 兜底行级越权；库级独享的千级运维成本仍不可接受 |
| ADR-205 | 绑定用事务级 `set_config(..., true)`，弃连接级 SET | 连接级设置在连接池下必然串号/失效（本迭代的真实教训） |
| ADR-206 | 越权返回 404 | 403 暴露资源存在性，给探测者信息 |
| ADR-207 | 越权测试矩阵进 CI | 隔离回归（新接口漏挂基类）靠 code review 不可靠 |
| ADR-233 | schema 隔离 + RLS 纵深并存 | RLS 单独覆盖不了租户生命周期，schema 单独兜不住 search_path 注入/跨 schema 全限定查询——双层互补 |

## 7. v2 的痛点

第二家客户上线（Free 计划），一周内把它当内部系统用——单日 Token 消耗是正常客户的 40 倍，白嫖了我们 40 倍的 LLM 成本。**SaaS 必须在信任任何租户之前先限量**。→ [03-迭代二-租户配额与限流.md](03-迭代二-租户配额与限流.md)
