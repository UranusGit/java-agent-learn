## 一、为什么上下文要做成平台

```mermaid
graph TB
    subgraph chaos["现状：各拼各的"]
        A["业务A: 硬截历史"]
        B["业务B: 超窗报错"]
        C["业务C: 用户输入放最前"]
        D["关键信息被截/预算失控/KV缓存全失效"]
    end
    subgraph hub["目标：上下文中枢"]
        H1["五层管线+优先级裁剪"]
        H2["分层配额+压缩"]
        H3["缓存友好层序"]
    end
    chaos -. 平台化 .-> hub
    style D fill:#ffcdd2
    style H1 fill:#c8e6c9
```

**三个核心论点**：

1. **裁剪要有底线**：系统提示与用户输入永不裁——各处硬截的根源是没有全局优先级。
2. **层序即缓存**：稳定内容前置，KV/Prompt Cache 命中率是层序设计的直接收益（省钱提速的另一半）。
3. **裁剪要可观测**：每次裁了什么、剩多少——成本审计与解释（30）的素材。

### 一.1 本节核对（为什么做平台）

- [ ] 能不看正文复述三个核心论点（裁剪有底线/层序即缓存/裁剪可观测），并各自对应到后续某一迭代篇（01/05/06）
- [ ] 「用户输入放最前→前缀变→KV 全失效」这条现状痛点在 01/05 中能找到对应落地（层序渲染/稳定前置）
- [ ] 现状「各拼各的」三条反例（硬截/超窗报错/输入放最前）未与目标「上下文中枢」的能力混淆
