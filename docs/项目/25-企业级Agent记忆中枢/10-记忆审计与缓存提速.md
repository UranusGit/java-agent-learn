## 四、召回缓存 + 索引提速

```java
// 概念代码：召回两级缓存(热点 + 索引)
public List<MemoryRecord> cachedRecall(String scope, String query, int topK) {
    String key = scope + ":" + sha256(query) + ":" + topK;
    // 一级 Caffeine 进程缓存(热) + 二级 Redis 共享缓存(冷) —— 响应 04/08 高频召回
    return caffeine.get(key, k -> redis.get(key, k2 -> hybridRecall(scope, query, topK)));
}
```

**注意**：缓存 **scope 维度 key**（多租户不漏读，呼应 05）；记忆变化/删除时**失效对应 key**（呼应 07 遗忘权，删记忆后缓存也立失效）。

### 四.1 本节测试与验证（召回缓存 + 索引提速）

**前置条件**：`cachedRecall(scope, query, topK)`（一级 Caffeine + 二级 Redis）已实现；能对同一 query 重复召回并观测延迟与命中。

**材料——缓存核对**（同 scope 同一 query 连续召回，对比首次/再次延迟）：

```text
同一 query 并发/连续触发 cachedRecall；随后故意修改/删除该记忆
```

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 首次 `cachedRecall(scope, q, k)` | 首次 miss 走 `hybridRecall`，命中并填充缓存 |
| 2 | 同 scope 同 query 再次召回 | 命中缓存（Caffeine 一级或 Redis 二级），延迟显著低于首次（热点召回提速） |
| 3 | 不同 scope 同 query | 不命中（key 含 scope，多租户不漏读，呼应 05） |
| 4 | 修改/删除该记忆后召回 | 对应缓存 key 失效，读到新值而非脏缓存（呼应 07 遗忘权） |

**失败排查**：①二次仍 miss→缓存 key 不稳定（如 query 未归一化）或未 put 成功；②跨 scope 命中→key 漏 scope 维度；③删记忆后仍读到旧→删除流程未失效对应 key。
