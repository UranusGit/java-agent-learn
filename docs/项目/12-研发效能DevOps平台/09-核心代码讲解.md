## 1. 六个关键设计复盘

### 1.1 为什么代码库 RAG 是"AST 分块"而非文本切块

代码不是自然语言——文本切块会把方法切开、丢失作用域链。JavaParser 按方法/类边界分块 + 作用域链元数据，Recall@5 +4.3（cAST 论文）。**代码 RAG 本质是"解析问题，不是检索问题"**——索引质量决定检索质量，检索质量决定所有下游（审查/测试/诊断）的质量。[01 §3.6-3.7] 的 `JavaChunk`/`JavaChunkIndexer` 是完整可手写实现。

### 1.2 为什么审查是"静态层先行 + LLM 收尾"

SAST+LLM 混合 F1 0.91-0.95 vs 纯 SAST 0.10-0.55 vs 纯 LLM 0.61-0.68（[调研 §SAST+LLM]）。静态层（SpotBugs/Semgrep）确定性抓硬问题，LLM 只做语义层收尾。**关键红线：禁止 LLM 自动 suppression 真阳性**——LLM 过滤 SAST 误报时会系统性误杀真漏洞（CWE-327 漏判率 77%）。[02 §3.6] 的 `SemgrepRunner` 直接解析 `--json` 输出，L1 处置由 SAST 规则判定。

### 1.3 为什么测试用"变异测试闸门"而非行覆盖率

行覆盖率可被 AI 刷分（92% 可编译但只杀 58-62% 变异 vs 人类 78%）——LLM 生成的测试能"跑过"但抓不住 bug。变异测试（PIT）注入变异体、测试必须杀死才有效，**不可刷分**。[03 §3.7] 的 `MutationGate` 解析 PIT 的 `mutations.xml` 算 kill rate，这是质量闸门的本质。

### 1.4 为什么多 Agent 评审要"强聚合层"

并行专业 Sub-Agent（安全/性能/架构/合规）各查一个维度，但评论会重复/矛盾。聚合层做四件事：语义去重、共识打分（严重度×命中 Agent 数）、幻觉过滤（无代码依据丢弃）、争议上抛 HITL。**聚合 Agent 禁止重新审查**——对撕式重审实证性降低 precision。[05 §3.6] 的 `ReviewAggregator` 完整实现这四步，`CodeIndexService.validLocation` 做幻觉过滤。

### 1.5 为什么评估要"盲评 + 误报率门槛"

LLM-judge 有过度纠正偏置（48.2% 假阴性来自泛化断言）与确认偏置（对抗性元数据可改变检出率 59.6pp）——必须脱敏盲评。**误报率是生死线（<5% 上线门槛）**：误报淹没开发者的后果比漏报更重。[07 §3.6] 的 `BlindJudge` 用脱敏 prompt（不含来源标注），`OnlineMetrics` 用 `Counter` 算 dismissed/total。

### 1.6 为什么私有代码安全要"检索前 Fail Closed"

事后过滤（先检索再删敏感代码）是结构性失败——敏感代码已经进了上下文/LLM。**权限过滤必须在 ANN pre-filter 层（元数据过滤），严禁 post-filter**；Fail Closed（无权限即拒绝，不静默跳过）。[08 §3.7] 的 `SecureCodeSearchService` 用 `filterExpression("department == ...")` 先过滤再检索。

### 1.8 本节测试与验证（AST 分块与静态先行——设计 1.1/1.2）

**前置条件**：`JavaChunkIndexer`（[01 §3.7](01-最小Demo搭建.md)）与 `SemgrepRunner`（[02 §3.6](02-代码审查Agent.md)）已实现；本地有一份含多方法 Java 工程副本（`repo.local-root` 指向它）。

**材料 A——分块对象**：一个含 3 个方法的 `OrderService.java`；**材料 B——SAST 样本**：一条 SpotBugs/Semgrep 可检出的硬编码密钥。

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 材料 A 走 `JavaChunkIndexer` 分块 | 每个方法一个 `JavaChunk`：`qualifiedName` 含 `#方法名`、`scopeChain` 非空（模块→包→类型）、`body` 不跨方法——**方法边界不被文本切断** |
| 2 | 对同一文件比对"文本切块 500 字符"与 AST 分块的 chunk 数与边界 | 文本切块把方法拦腰截断；AST 分块边界与方法起止一致（Recall 差异的根源可复现） |
| 3 | 材料 B 走 `SemgrepRunner`（`--json`） | 输出 JSON 被解析为 `StaticFinding` 列表，L1 处置由 SAST 规则判定（`ReviewAgent` 不再让 LLM 复核真阳性） |
| 4 | 人工把材料 B 的 finding 标记为真阳性后重审 | LLM **无权** suppression 该 finding（红线：CWE-327 类漏判率 77% 的教训） |

**最小可执行载体**（JUnit 5，纯 Java 不依赖 LLM；`mvn test -Dtest=JavaChunkIndexerTest`）：

```java
@Test
void AST分块_方法边界不切断() {
    // 材料 A：3 个方法的类 → 3 个 chunk，边界=方法起止（1.1 解析问题而非检索问题）
    List<JavaChunk> chunks = indexer.index(Path.of("OrderService.java"), "core");
    assertThat(chunks).hasSize(3);
    assertThat(chunks).allSatisfy(c -> {
        assertThat(c.qualifiedName()).contains("OrderService#");
        assertThat(c.scopeChain()).isNotBlank();   // 作用域链元数据（引用溯源与过滤的依据）
        assertThat(c.body()).doesNotContain("public void "); // 方法内不混入下一方法签名
    });
}
// mvn test -Dtest=JavaChunkIndexerTest → Tests run: 1, Failures: 0, Errors: 0
```

**失败排查**：①chunk 数不符→分块粒度配置成了类级（应为方法级）；`body` 混入下个方法→`MethodVisitor` 结束回调没对齐花括号层级；③finding 为空→`repo.local-root` 配错或 Semgrep 规则集未装（对照 [02 §3.6](02-代码审查Agent.md) 失败排查）。

### 1.9 本节测试与验证（变异闸门 / 强聚合 / 盲评 / pre-filter——设计 1.3-1.6）

**前置条件**：`MutationGate`（[03 §3.7](03-测试生成Agent.md)）、`ReviewAggregator`+`CodeIndexService.validLocation`（[05 §3.6/§3.3](05-多Agent评审流水线.md)）、`BlindJudge`（[07 §3.6](07-评估闭环.md)）、`SecureCodeSearchService`（[08 §3.7](08-私有代码安全.md)）已实现。

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 用真实 PIT `mutations.xml`（kill 3/5）喂 `MutationGate` | `killRate` 解析得 0.6；payment/security 模块 `passes` 返回 false（阈值 85%）、default 模块返回 true（阈值 65%）——闸门阈值按模块分级 |
| 2 | 四专家评审同一 PR，两条评论同 `file#line#category`；另有一条评论的 line 超出文件实际行数 | 聚合后 dedup 合并为一条且 `consensus` 计数 ≥ 2；幻觉评论被 `validLocation` 丢弃，不出现在 `ReviewReport.grounded` |
| 3 | 构造 critical 评论被另一 Agent 矛盾的场景 | `findDisputes` 产出 `Disputed` 上抛 HITL——聚合层**不静默采纳任一方**，且 `aggregate` 全程零 LLM 调用 |
| 4 | 对比 `BlindJudge.toBlindPrompt(c)` 与原评论 | 只含 `file:line + message`，**不含**"AI 生成/人工"来源标注（防确认偏置 59.6pp 的教训） |
| 5 | user A（`department=platform`）检索，user B（`department=app`）检索同一 query | 两次 `filterExpression("department == '<user 的部门>'")` 值不同且在**检索前**生效——B 的结果集不含 platform 仓库 chunk（pre-filter，非事后删除） |

**curl 载体**（端到端复核评审链路，端口 8081、profile devops）：

```bash
# 触发四专家评审（fan-out → 聚合），断言响应含 dedup 后评论与 disputes 字段
curl -s -X POST http://localhost:8081/api/v1/review/core/101
# 反馈三态落 review_outcome（v7 OnlineMetrics 的 dismissed/total 分母来源）
curl -s -X POST http://localhost:8081/api/v1/review/feedback -H "Content-Type: application/json" \
  -d '{"commentId":"c-1","outcome":"DISMISSED"}'
```

**失败排查**：①`killRate` 为 0 → `mutations.xml` 路径错（PIT 报告目录）或 XML 元素名解析错；②dedup 未合并 → key 漏了 `category` 段或行号类型不一致（String vs int）；⑤越权可见 → `filterExpression` 拼接在 `SearchRequest` 构建之后（成了 post-filter）或用户部门解析取了请求参数而非 JWT claim（[08](08-私有代码安全.md) `JwtPrincipalResolver` 纪律）。
