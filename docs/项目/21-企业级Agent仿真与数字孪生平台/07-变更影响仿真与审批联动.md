# 07-变更影响仿真与审批联动——仿真即闸门

> **定位**：收官闭环：变更单（Prompt/模型/工具/配置）→ 自动触发的定向仿真（04 场景）→ 影响报告（diff/降级/容量三类）→ **HITL 审批**（报告作为审批证据）→ 与发布流程联动（仿真未过不放行）。仿真从"平台里的一张报告"变成"发布流水线的硬闸门"。读者画像：要回答"怎么强制每个变更先仿真"的读者。前置阅读：[06-容量与压测](06-容量与压测.md)、[教程 30-HumanInTheLoop]、[教程 29-灰度发布]。
>
> **铁律 0**：变更单模型与联动自研「概念代码」；HITL 落点遵循已实证基准（工具/流程装饰层）。

## 一、四问

| 问 | 答 |
|----|----|
| **新增了什么需求** | ① 变更单类型化：Prompt/模型切换/工具改描述或换源/配置阈值——每类绑定默认仿真套餐（Prompt→场景 diff；模型→diff+容量；工具→降级彩排）② 报告即证据：审批页内嵌仿真报告（差例可点、彩排结果、拐点）——审批人看证据不靠口头描述 ③ 闸门硬约束：CI/CD 中仿真未过/未跑 → 发布流水线拒绝（可按变更风险分级豁免，豁免需双签）④ 仿真-生产对照回流：上线后实测 vs 仿真预测的偏差回写（10 校准孪生的数据源） |
| **影响了哪些模块** | 新增 `change-gate`；对接发布流水线（Webhook）与审批（HITL 队列） |
| **架构如何演进** | 仿真工具 → 仿真闸门（六迭代能力收口成一个动作：放行/打回） |
| **上一版痛点** | 报告躺在平台里，发布不看它：仿真跑不跑靠自觉、审批人问"应该没问题吧"（06 §六） |

**本迭代验收**：① 未过仿真的变更发布被流水线拒绝 100%（旁路豁免需双签留痕）② 审批页报告内嵌可交互 ③ 变更-仿真-审批-发布-回流五环事件链完整可审计 ④ 风险分级正确（低风险配置变更走快速通道 ≤10min）。

## 三、变更分级与豁免纪律

| 级别 | 例 | 套餐 | 审批 |
|------|----|------|------|
| 高 | 模型切换/工具换源 | diff+彩排+容量全跑 | 双人审批 |
| 中 | Prompt 主体改动 | 定向 diff+相邻场景 | 单人+报告 |
| 低 | 文案/阈值微调 | 快速抽样 diff | 自动+抽审 |

- **豁免必须贵**：跳过仿真需要变更人+平台 owner 双签，豁免单月公示——让"走后门"有成本，闸门才是闸门。

## 四、仿真-生产偏差回流

- 上线 48h 内：生产实测指标 vs 仿真预测逐项对照；偏差 >15% 记失真事件（孪生环境的健康度输入，10 展开）。
- 回流让闸门自我进化：长期偏差小的场景可提级为"低风险自动放行"，偏差大的场景强制全跑。

## 五、仿真执行进度可见（结合 变更单/Replay/Scenario 完整实现）

> 过程可见性是工业级标配。仿真是**批量回放/注入**任务，用户要实时看到"回放到哪、注入的故障是否生效、哪个场景在跑"——尤其故障彩排（05）必须看到故障真的注入了。下面是一段**可编译的完整实现**，挂在真实仿真执行器（变更单驱动的 `twin-svc` 回放/注入链）的每个回放单元与注入点：

```java
package twin.engine;

import reactor.core.publisher.Flux;
import reactor.core.publisher.Sinks;

/** 仿真过程可见：每个回放/注入/断言发事件，faultApplied 确认注入真的生效。 */
public final class SimProgressEmitter {
    private final Sinks.Many<SimEvent> sink = Sinks.many().unicast().onOverflowBuffer();
    private int replayed;

    public sealed interface SimEvent {
        String changeId(); String scenario(); Stage stage();
        record Replayed(String changeId, String scenario, Stage stage, int current, int total)
            implements SimEvent {}
        record FaultInjected(String changeId, String scenario, Stage stage, String fault, boolean applied)
            implements SimEvent {}
        record Asserted(String changeId, String scenario, Stage stage, boolean pass)
            implements SimEvent {}
        enum Stage { REPLAY, FAULT_INJECT, ASSERT }
    }

    public Flux<SimEvent> events() { return sink.asFlux(); }

    /** 每回放一例调用。 */
    public void onReplayed(String changeId, String scenario, int total) {
        sink.tryEmitNext(new SimEvent.Replayed(changeId, scenario, SimEvent.Stage.REPLAY, ++replayed, total));
    }
    /** 注入故障后必须带上 applied（确认注入真实落到被测链路）。 */
    public void onFault(String changeId, String scenario, String fault, boolean applied) {
        sink.tryEmitNext(new SimEvent.FaultInjected(changeId, scenario, SimEvent.Stage.FAULT_INJECT, fault, applied));
    }
}
```

| 维度 | 事件 | 用户看到 |
|------|------|---------|
| 回放 | `Replayed{current,total}` | "回放 320/1000 例" |
| 注入 | `FaultInjected{applied}` | "已注入 stock 超时→生效=true" |
| 断言 | `Asserted{pass}` | "该场景降级断言通过" |

**四条纪律**：① **故障注入必须确认生效**（`applied=true`）——仿真最怕"以为注入其实没注入"白跑；② Replayed 进度使大批量可中断续跑；③ 场景粒度（`scenario` 定位"哪类挂了"）；④ `Asserted.fail` 可触发立即中止策略（供闸门/演练）。

## 六、验证包（手工测试与验证）
**前置条件**：变更单+套餐绑定+审批内嵌报告+CI 拒绝门实现。

**材料 A——三类变更单**：高（模型切换）/中（Prompt 改动）/低（文案）各一。

**步骤与断言**：

| # | 操作 | 预期（PASS 判据） |
|---|------|------------------|
| 1 | 跳过仿真直接发布 | 流水线拒绝 100%；豁免双签+进公示 |
| 2 | 高风险单 | diff+彩排+容量全跑；审批页差例按 caseId 可点开 |
| 3 | 低风险单 | 全流程 ≤10min |
| 4 | 上线 48h 回流 | 实测 vs 预测偏差出数（>15% 记失真） |
| 5 | 五环审计 | 变更→仿真→审批→发布→回流日志完整 |

**失败排查**：①可绕过→CI 门不在必经路径，应移 pipeline gate；②点不开→caseId 未入报告；④无回流→埋点缺失。
