## 一、一次模型发布的边缘旅程

```mermaid
sequenceDiagram
    participant OP as 运营
    participant HUB as edge-hub
    participant REG as Registry
    participant CAN as 金丝雀组
    participant N as 普通节点
    participant NET as 网络

    OP->>REG: 上传 v2 包(manifest+签名)
    REG->>CAN: 灰度5%(带宽预算错峰)
    CAN->>HUB: 验证指标OK
    HUB->>N: 全量分组分发(断点续传)
    NET--)N: 某区域断网!
    N->>N: 04降级: 本地栈+显式告知
    N->>N: 分发暂存(恢复续传)
    N->>HUB: 恢复: 续传+验签+双槽切换
    HUB->>OP: 发布完成(2节点断网自愈记录)
```

### 一.1 本节核对（一次模型发布的边缘旅程）

- [ ] sequenceDiagram 中每个参与者（运营/hub/Registry/金丝雀组/普通节点/网络）与后续迭代（03 分发 / 04 降级 / 06 验签）一一对应，主线完整无断点
- [ ] "断网→分发暂存→恢复续传+双槽切换"能复述为一条闭环（发布中途区域断网仍自愈完成）

## 四、最容易踩的三个坑

1. **模型更新全量齐发** → 专线打满。**解法**：带宽预算+错峰（03）。
2. **断网静默装正常** → 用户信任崩塌。**解法**：显式告知（04）。
3. **弱节点硬扛重负载** → 卡死。**解法**：局域互援（08）。

### 四.1 本节核对（最容易踩的三个坑）

- [ ] 三个坑（更新风暴/断网装正常/弱节点硬扛）各有一个明确解法（03 带宽+错峰 / 04 显式告知 / 08 局域互援），无"知道坑但不知解法"的空洞项
- [ ] 三条解法的迭代落点与三/分层职责表一致
