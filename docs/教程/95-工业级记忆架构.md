## 1. 记忆不是"一个数据库"，是三层的读写架构

### 1.1 三层记忆的本质差异

| 层 | 载体 | 读方式 | 生命周期 | 典型内容 |
|----|------|--------|---------|---------|
| **工作/会话记忆** | `ChatMemory`（会话内） | `get(conversationId)` 全窗口 | 会话结束即回收 | 本次对话的交互 |
| **长期语义记忆** | 自研 `ChatMemoryRepository`（持久化） | 关键字/摘要/评分检索 | 长期存留 + 演化衰减 | 用户偏好、事实、结论 |
| **外部 RAG** | 向量库 | embedding 相似度 | 知识库文档 | 文档、规范、手册 |

**核心**：三层不是"三个表"，而是**三层不同的读写协议**——会话内是"全量窗口"，长期是"选择性召回"，RAG 是"语义检索"。工业化的第一步就是**明确每层的读写语义**（呼应 [39](../教程/82-高级记忆架构.md) 的三层定义）。

## 2. 记忆的读写：从概念到 API

### 2.1 会话/工作记忆（Spring AI 官方基准）

```java
// Spring AI 2.0.0 —— ChatMemory 官方 API（javap 实证）
ChatMemory memory;   // = InMemoryChatMemoryRepository 自动装配
memory.add(conversationId, new UserMessage("我偏好深色主题"));  // 写入工作记忆
List<Message> recent = memory.get(conversationId);              // 读全量窗口(单参)
```

### 2.2 长期记忆（自研持久化，implements 官方接口）

官方库只有内存实现，**长记忆必须自研 `ChatMemoryRepository`**（CLAUDE.md 铁律明确无官方 Jdbc/Redis 实现）：

```java
// 概念代码：长期记忆持久化 + 语义检索（自研 implements ChatMemoryRepository）
@Component
public class SemanticMemoryRepository implements ChatMemoryRepository {
    private final PgVectorStore vectorStore;      // 语义检索(embedding相似度)
    private final JdbcTemplate jdbc;              // 事务/元数据/衰减字段

    @Override public List<Message> findByConversationId(String conversationId) {
        return jdbc.query("SELECT... WHERE conversation_id=?", ...);
    }
    @Override public void saveAll(String conversationId, List<Message> messages) {
        for (Message m : messages) {
            jdbc.update("INSERT INTO memory_store(conv_id, role, content, ts, score)...", ...);
            vectorStore.add(Document.builder().id(...).content(m.getText()).build());// 语义索引
        }
    }
    // 语义召回：按相关度(score)而非全量
    public List<Message> semanticRecall(String query, int topK) {
        return vectorStore.similaritySearch(query, topK).stream()...;
    }
    @Override public void deleteByConversationId(String cid) { ... }   // 被遗忘权
}
```

**要点**：长期记忆的**读**是"选择性召回"（语义/按 score），不是像短记忆那样全窗口——否则长记忆越多越超 Token（呼应 [77-上下文工程](77-上下文工程.md) 的 Token 预算）。

## 3. 记忆的演化与衰减

记忆不是静态存储，会**演化**（更新）与**衰减**（遗忘）——否则过期偏好/错误事实会一直误导 Agent。

```java
// 概念代码：记忆矩阵(score) + 衰减作业
record MemoryRecord(String id, String content, long lastAccessTs, double score) {}

// 每被召回一次加分；长时间不召回衰减（阿林琴:分区分割曲线）
public double decay(double score, long ageDays) {
    return score * Math.exp(-LAMBDA * ageDays);   // 指数衰减
}
public double reinforce(double score) { return Math.min(score + DELTA, 1.0); }
```

**规则**：**反复命中 + 长期稳定 → 长期保留**；**长期不被召回 → 衰减到阈值下则归档/清理**。配合 `findByConversationId` 支持查询，`deleteByConversationId` 支撑被遗忘权。

## 4. 记忆冲突与一致性

同一用户/同一主题，新旧记忆可能**冲突**（旧说"偏好A"，新说"偏好B"）。工业级要**冲突消解**：

| 冲突类型 | 处理 |
|---------|------|
| 时间新者胜 | 取最近时间戳（大多偏好类冲突） |
| 置信度评分 | 保留高 score 的（可被反复强化） |
| 相互矛盾 | 同时给 Agent 呈现"新旧两个版本 + 时间"，让 LLM 结合上下文判断 |

## 5. 多 Agent 共享记忆的读写隔离

多 Agent 用同一记忆中枢时（呼应 [09-多Agent协作](09-多Agent协作.md)、[26-多租户隔离](59-多租户隔离与资源治理.md)），必须**读写隔离**：

```java
// 概念代码：记忆作用域（租户×Agent×会话 隔离键）
record MemoryScope(String tenantId, String agentId, String conversationId) {
    static String partitionKey(MemoryScope s) {
        return s.tenantId() + ":" + s.agentId() + (s.conversationId()!=null ? ":"+s.conversationId() : "");
    }
}
```

**要点**：记忆必须**按 scope 分区**（tenant:agent[:conv]），否则多租户/多 Agent 互相污染记忆——这是多租户隔离在"记忆"这一资源上的落地（呼应 [59-多租户隔离与资源治理](./59-多租户隔离与资源治理.md)）。

## 6. 被遗忘权（GDPR）

用户要求删除自己的记忆时必须可删（呼应 [58-历史记录持久化与合规](58-历史记录持久化与合规.md)、[43-治理](86-Agent治理与合规框架.md)）：

```java
// 官方接口 deleteByConversationId 就是被遗忘权的触点
memoryRepository.deleteByConversationId(conversationId);
// 细粒度：按用户维度×主题 批量删(自研：DELETE FROM memory_store WHERE tenant=? AND user_id=?)
```

**必须**：①可审计（谁请求删了什么）②级联删向量索引与元数据 ③有保留期默认值。

## 7. 记忆与 Token 预算

每次把记忆灌进上下文都要花 Token（呼应 [77-上下文工程](77-上下文工程.md)、[27-成本治理](60-成本治理与Token计量.md)）。原则：**按 token 预算召回，而不是按相关度无上限**：

```java
// 概念代码：Token 预算内召回(短记忆窗口 + 长记忆topK + RAG)
public MemoryPacket recallWithinBudget(String convId, String query, int tokenBudget) {
    List<Message> shortWin = new ArrayList<>(chatMemory.get(convId));      // 短记忆全窗口
    int left = tokenBudget - estimateTokens(shortWin);                     // 扣掉短记忆后剩余预算
    List<Message> longHit = longMemory.semanticRecall(query, budgetToTopK(left)); // 长记忆按剩余预算算topK
    int left2 = left - estimateTokens(longHit);
    List<Document> ragHit = vectorStore.similaritySearch(query, budgetToTopK(left2));  // RAG
    return new MemoryPacket(shortWin, longHit, ragHit);                     // 三层都 fit 进预算
}
```

```

**要点**：上下文是"五层拼接 + Token 预算分配"（[77-上下文工程](77-上下文工程.md)）。记忆只是其中一层，**每层都要 fit 进预算**——记忆召回过剩会挤掉系统提示/用户输入。

## 8. 适用场景与不适用场景

### 适用场景 ✅
- 需要跨会话记住用户偏好/长期事实，且要**语义召回、可衰减、可删除**的生产 Agent。
- 多租户/多 Agent 需**记忆隔离**、有 GDPR 被遗忘权需求的合规系统。

### 不适用场景 ❌
- 单会话临时对话，短记忆 `ChatMemory` 即够（无需长期层）。
- 需要超低延迟读取数十万条记忆的海量场景——需专属记忆 KV/缓存，通用三层架构会成瓶颈。

## 总结

工业级记忆架构，是把 [82-高级记忆架构](82-高级记忆架构.md) 的三层理论变成**可运维、可演化、可治理**的系统。本章建立五根支柱：

1. **三层读写协议**：工作记忆全窗口 / 长期语义语义召回 / RAG 相似度，彼此读写语义不同。
2. **官方基座**：`ChatMemory`(短) + 自研 `ChatMemoryRepository`(长)（javap 实证，CLAUDE.md 铁律）。
3. **演化衰减**：score 强化 + 指数衰减，过期/错误记忆自动淡出。
4. **冲突消解 + 读写隔离**：时间/评分消解；tenant:agent:conv 分区防污染。
5. **被遗忘权 + Token 预算**：`deleteByConversationId` 支撑 GDPR；每层 fit 进上下文预算。

> **实操建议**：先用 `ChatMemory` 跑通短记忆，再自研 `ChatMemoryRepository` 加持久化 + 语义召回，最后补衰减/隔离/GDPR。落地完整企业平台 → [项目25-企业级Agent记忆中枢](../项目/25-企业级Agent记忆中枢/00-需求分析与架构设计.md)。
