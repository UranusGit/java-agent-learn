# 图类型选择：先认清读者要理解的结构

选图的唯一依据是**这段内容里读者真正要理解的是什么结构**，不是内容的表面名词。
同一句话叫"流程"，可能是线性步骤、可能是多角色交互、可能是状态迁移——三种结构对应三种图。

**决策顺序：先认清结构 → 再选图类型 → 最后考虑易读性。**

---

## 一、认清结构：这段内容读者要理解什么？

先把内容对应到下面的结构之一。**结构决定了图类型，而不是内容话题。**

| 结构（读者要理解什么） | 一句话特征 | 首选图 | 备选 / 何时换 |
|---|---|---|---|
| **线性步骤** | 一个主体按顺序做几步，无交互 | `flowchart TD` | 步骤 ≤2 步 → 不用图，一句话 |
| **分支决策** | 一个点分多路（是/否、多选一） | `flowchart`（菱形 `{ }` 判断） | 分支多且层层嵌套 → 拆图或换 stateDiagram（若本质是状态迁移） |
| **多角色交互** | 多个参与方来回发消息/调用，强调**谁调谁、先后顺序** | `sequenceDiagram` | 纯数据流不强调时序 → `flowchart LR` |
| **状态迁移** | 一个对象在不同状态间转移，有**状态名词**和**触发条件** | `stateDiagram-v2` | 只有 2 个状态 → 用文字；状态 + 分支混着 → 拆成状态图和流程图两张 |
| **分层 / 组合 / 架构** | 系统由哪些部分组成、怎么分层、组件间依赖 | `flowchart`（`subgraph` 分组） | 纯分类不表达依赖 → `mindmap` |
| **实体关系 / 数据模型** | 表、实体、外键、一对多/多对多 | `erDiagram` | 面向对象的类关系 → `classDiagram` |
| **类 / 继承 / 接口** | 类、继承、实现、接口、泛型 | `classDiagram` | 只有继承一条线 → 用文字 |
| **层级分类 / 头脑风暴** | 内容怎么分类组织，无箭头关系 | `mindmap` | 有箭头/依赖 → `flowchart` |
| **时间线 / 里程碑顺序** | 按时间先后的事件的先后 | `timeline` | 有持续时长/依赖 → `gantt` |
| **占比 / 分布** | 一部分占整体多少 | `pie` | 多系列对比 → `xychart-beta` |
| **排期 / 任务依赖** | 任务什么时候做、谁依赖谁 | `gantt` | 只看先后不看时长 → `timeline` |

## 二、最容易选错的四组（重点）

**1. "流程"不一定画 flowchart——先看有几个角色**
- 一个主体依次执行：`flowchart TD` ✅
- 客户端⇄服务端⇄数据库三方交互：`sequenceDiagram` ✅
- 判断标准：**图里有没有"谁发给谁"的横向消息**？有 → 时序图；只是"上一步到下一步" → 流程图。

**2. "状态"和"分支"不是一回事**
- 状态迁移（订单：待支付→已支付→已完成）：`stateDiagram-v2` ✅
- 分支决策（是否超时→是/否两个动作）：`flowchart` 菱形 ✅
- 判断标准：**节点是"状态名词"还是"动作"？** 状态名词（待支付/已支付）→ 状态机；动作（检查/发送/返回）→ 流程图。
- 混在一起时拆两张图：状态图讲"有哪些状态、怎么迁移"，流程图讲"某个状态里做了什么判断"。

**3. "分层"和"分类"不是一回事**
- 组件间有依赖/调用（前端→服务→DB）：`flowchart` + `subgraph` ✅
- 纯归类不表达依赖（技术栈分后端/前端/数据库）：`mindmap` ✅
- 判断标准：**层之间有没有箭头（依赖/调用/流向）？** 有 → 流程图；只是嵌套分类 → 思维导图。

**4. "实体关系"优先 erDiagram，不是 classDiagram**
- 数据表、外键、一对多：`erDiagram` ✅
- 类、继承、接口、方法：`classDiagram` ✅
- 判断标准：讲的是**存储的数据模型**（表结构）还是**代码的类结构**（继承/接口）？前者 erDiagram，后者 classDiagram。

## 三、选对类型后：怎么画才让读者省力（易读性）

选对类型只是第一步，**画法决定读者能不能一眼看懂**：

1. **一张图只讲一个结构。** 状态+分支混着、架构+时序混着 → 拆成两张。一张图试图说明太多，读者反而记不住。
2. **方向跟着阅读习惯。** 主流程竖排用 `TD`（从上往下读最自然）；横向对比/时间从左到右用 `LR`。别用 `TB`（少数字面含义 TD/TB 相同，统一 TD 减少噪音）。
3. **主干突出。** 主流程节点用 `[ ]`，关键判断用 `{ }`，起止用 `( )`——读者先扫形状就能定位"哪是判断、哪是终点"。
4. **节点文字短。** 一个节点一句话以内，动词或名词短语；超长文字拆到箭头标签或旁边说明里。节点太长 → 横躺长条，难读。
5. **箭头标签承载"条件/结果"。** `C -- 是 --> D`、`C -- 否 --> E` 比"`C-->D`、`C-->E`"让读者少想一步。
6. **subgraph 表达"组"，别用箭头表达"组"。** 组件属于哪一层用 `subgraph` 括起来，层与层之间的箭头只表达真实的依赖/调用。
7. **超过 12~15 个节点的图，拆。** 按主题拆成多张小图，或先画分层总览再逐层展开。一张塞不下的图 = 没人读得完的图。
8. **时序图控制参与者在 3~6 个。** 参与者太多，生命线交错，读者盯不住。超过就拆场景或归并参与者。
9. **状态图把"触发条件"写边上。** `待支付 --> 已支付 : 支付成功` 比裸箭头好懂——读者知道为什么迁移。

## 四、图对读者的价值自检（画完问自己）

- [ ] 我这张图，读者**第一眼**能找到主流程 / 主干吗？
- [ ] 每个节点 / 边都承载信息吗？有没有删掉也不影响理解的节点？（有 = 删）
- [ ] 读者**只看图**能理解 80% 的内容吗？剩下 20% 需要回正文才能懂 → 图的信息密度不够。
- [ ] 这张图比纯文字**省了多少思考时间**？说不出来 = 图没有信息增益，删（见 SKILL.md「第一原则」和"光杆子链"禁令）。
- [ ] 节点数超 15 了吗？超了 = 拆图。

> 图是让读者**少费一次力**的工具。如果一张图读者要读三遍才懂，它就不合格——哪怕它语法正确、类型"按理"对。
