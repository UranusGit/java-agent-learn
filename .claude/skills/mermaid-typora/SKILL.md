# Mermaid 图生成（Typora 兼容）

把"需要表达结构"的内容落地为格式正确、能直接渲染的 Mermaid 代码块。

## 第一原则：要不要图

图的价值是让读者**更快、更省力**地理解。画图前过三道判断，都通过才画：

1. **有结构吗？** 分支 / 并发 / 分层 / 时序 / 状态迁移 / 实体关系——纯叙述不需要图。
2. **一句话或表格能说清吗？** 一两个箭头用一句话，两列二维用表格。文字和表格比图省阅读成本。
3. **图比文字更快被理解吗？** 不是只为"看起来专业"。图必须比被替代的文字更快，否则别画。
4. **禁止"光杆子"链。** 从上到下一条线串到底、无分支无对比无交互的图 = "列表换个框"，毫无信息增益——不画，改用表格或一句话。画图前自问"哪里有分叉 / 交互 / 对比 / 状态迁移？"一个都没有就别画。自我检查：图里必须至少有 `{ }` 判断、或 ≥2 条平行支路做对比、或多参与者交互、或状态迁移。

> 正文讲**为什么/取舍/异常**；图展示**结构/顺序/依赖**。图是正文支撑，别让正文逐节点复述图（= 双重叙述）。
> 质量底线：每个节点/边都承载信息；单图 ≤ 12~15 节点（超了拆）；宁缺毋滥——烂图不如没有。

## 选哪种图（先认清结构，不看名词）

**选图看读者要理解的结构，不看内容叫"流程"还是"时序"。** 同一"流程"可能是线性步骤、多角色交互、状态迁移——三种结构三种图。选错读者就难懂。拿不准选型时读 `references/选型决策.md`（四组详解）。

| 结构（读者要理解什么） | 首选图 | 何时换 |
|---|---|---|
| 一个主体的线性步骤 / 分支决策 | `flowchart`（判断用 `{ }`） | 多角色交互 → 换时序图 |
| 多角色来回发消息 / 调用 | `sequenceDiagram` | 纯数据流不强调时序 → flowchart |
| 状态迁移（状态名词 + 触发条件） | `stateDiagram-v2` | 状态和分支混着 → 拆两张图 |
| 分层 / 组件依赖 / 架构 | `flowchart` + `subgraph` | 纯分类无依赖 → mindmap |
| 实体关系 / 数据模型 | `erDiagram` | 类/继承/接口 → classDiagram |
| 类、继承、接口、泛型 | `classDiagram` | 只有继承一条线 → 用文字 |
| 层级分类、头脑风暴 | `mindmap` | 有箭头依赖 → flowchart |
| 时间线、里程碑顺序 | `timeline` | 有持续时长/依赖 → gantt |
| 占比、分布 | `pie` | 多系列对比 → xychart-beta |
| 排期、任务依赖 | `gantt` | 只看先后 → timeline |
| git 分支 / CI 流程 | `gitGraph` | — |
| 报文 / 协议字段布局 | `packet-beta` | — |
| 问题原因分析 | `ishikawa` | — |

**最容易选错的四组**（完整版见 `选型决策.md`）：
1. 流程 ≠ 流程图——多角色交互该用时序图
2. 状态 ≠ 分支——状态名词用状态机，动作判断用流程图菱形
3. 分层 ≠ 分类——有依赖/调用用 flowchart，纯归类用 mindmap
4. 实体关系优先 erDiagram，不是 classDiagram

### 易读性画法（每张图都该做到）

- **方向**：主流程竖排 `TD`（从上往下），横向对比/时间 `LR`。
- **主干突出**：主流程 `[ ]`、判断 `{ }`、起止 `( )`——读者先扫形状定位关键点。
- **节点文字短**：一个节点一句话以内；超长拆到箭头标签或说明。
- **箭头带条件**：`C -- 是 --> D` 比裸 `C-->D` 少让读者想一步。
- **一张图只讲一个结构**：状态+分支、架构+时序混着 → 拆两张。
- **单图 ≤ 12~15 节点**，时序图参与者在 3~6 个。

## 三个铁律

1. **用 Mermaid，不用 ASCII 字符画。** 一旦决定画图就输出 ```` ```mermaid ````；文档里已有字符画且确实需要图时，按 `references/文本流程图转换.md` 改写。
2. **Typora 兼容。** 只用 Typora 内置 Mermaid 11.x 稳定语法；避免 `-beta` 实验图和 `flowchart-elk`/`graph-elk`。拿不准查 `references/Typora兼容性.md`。
3. **语法必须完整可渲染。** 写完过一遍自查清单（见下）。

## 通用语法（所有图）

- 语言标识必须 `mermaid`。
- **统一用 `flowchart`，不写旧版 `graph`。** 两者等价但 `flowchart` 更现代、解析更稳。
- **含特殊字符的标签加双引号**：`( ) [ ] { } : # "` 都会报错或乱码。拿不准就加：`A["计算 (含公式)"]`、`A["状态: 完成"]`。
- 纯中文直接写不需要引号：`A[用户提交订单]`；中文混入特殊字符时整标签加引号。
- **节点换行用 `<br/>`**：`A["第一行<br/>第二行"]`；含 `<br/>` 的标签记得加双引号。
- **ID 用英文小写/下划线**，显示文本放标签里：`participant client as 客户端`；同一图 ID 唯一。
- **一个代码块只放一张图**，不用 `&&` 分隔；紧跟正文后。
- 注释 `%%`；配置 `%%{init:{...}}%%` 放第一行、最小化。
- `classDiagram` 类名/成员名、`erDiagram` 实体名用英文；中文语义放 `note` 或关系标签。

## 生成流程

1. 按「第一原则」判断要不要图。不需要 → 一句话或表格，结束。
2. 按速查表把内容对到结构（线性/交互/状态/分层/关系/分类/时间线），选图类型。**拿不准选型时**才读 `references/选型决策.md`（四组详解 + 易读性画法）。
3. **必须读对应 reference 取模板（`references/<类型>.md`）再写，别凭记忆。** reference 里是该图类型的完整语法、示例和「常见坑」——跳过它会漏掉 Typora 特有细节（引号、`<br/>`、勿用 `graph` 等）。
4. 套模板写 mermaid，套「通用语法」，按「易读性」画法检查（主干突出、节点文字短、箭头标签带条件）。
5. 文档里已有 ASCII 流程图且需要图 → 按 `references/文本流程图转换.md` 转换。
6. 过自查清单。**若用户反馈 Typora 渲染失败 → 按 `references/Typora兼容性.md` 的「渲染失败排查清单」逐项排查修复。**
7. **批量文档作业时，生成完用本地校验闭环验证**：按 `references/Typora兼容性.md` 的「本地批量校验方法」（Node + `mermaid@11.13.0`）解析所有生成的代码块，全部通过再交付。

## 输出前自查（核心 5 项）

- [ ] 真的需要这张图吗？一句话或表格能否替代？
- [ ] **图类型匹配结构吗？** 多角色交互用时序图？状态迁移用状态机？层级分类用 mindmap？（见 `选型决策.md`）
- [ ] 读者第一眼能找到主流程/主干吗？
- [ ] 语言标识 `mermaid`；含特殊字符的标签都加了引号？
- [ ] 引号/括号成对闭合；ID 唯一；缩进一致（仅缩进敏感的图：mindmap/timeline/复合状态）？
- [ ] 图类型关键字正确、无 `-beta`/`flowchart-elk`、一块一图、无 `&&` 多图？

> 通用规则（引号、ID、`<br/>`、勿用 `graph`）在「通用语法」；各图类型的特殊检查点见其 reference「常见坑」。
